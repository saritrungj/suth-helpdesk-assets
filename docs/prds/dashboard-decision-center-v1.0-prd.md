# Dashboard Decision Center - Product Requirements Document (PRD)

## Requirements Description

### Background

- **Business Problem:** หน้า Dashboard, Compare และรายงานตามฝ่าย/แผนกมีข้อมูลและตัวเลือกซ้ำกันหลายชุด ผู้ใช้ต้องจำว่าตัวเลขแต่ละหน้าใช้ขอบเขตใด และบางตัวกรองยังอิงข้อมูลปัจจุบันแทนข้อมูลที่มีผลในเดือนย้อนหลัง จึงเสี่ยงต่อการอ่านยอดผิดและไม่ตอบคำถามเรื่องลดต้นทุนได้ตรงจุด
- **Target Users:** หัวหน้าหน่วยงานที่ต้องตรวจการใช้เครื่องพิมพ์ เปรียบเทียบหน่วยงาน และจัดทำรายงานเพื่อประกอบการตัดสินใจ
- **Value Proposition:** กำหนดขอบเขตครั้งเดียว แล้วใช้ข้อมูลชุดเดียวกันกับตัวเลข กราฟ ตาราง รายละเอียด Excel และ CSV เพื่อระบุว่าเครื่องหรือหน่วยงานใดใช้มาก ใช้น้อย มีต้นทุนต่อเครื่องเท่าใด และข้อมูลพร้อมตัดสินใจหรือยัง
- **Success Metrics:** ผู้ใช้ระบุขอบเขตและตอบคำถาม “ใครใช้เท่าไร เมื่อใด และมาจากเครื่องใด” ได้จากหน้าเดียว; ตัวเลขบนหน้าจอและไฟล์ส่งออกตรงกัน; ไม่มีการเลือกอันดับให้โดยไม่บอก; รายงานย้อนหลังใช้สถานที่ หน่วยงาน สัญญา และราคาที่มีผลจริงในเดือนนั้น

### Feature Overview

- **Core Features:**
  - ตัวกรองกลางสำหรับปีงบ ช่วงเวลา ฝ่าย แผนก สัญญา อาคาร และเครื่อง โดยเลือกหลายรายการได้
  - KPI ของขอบเขตเดียวกัน ได้แก่ ค่าใช้จ่ายที่ยืนยันแล้ว ยอดพิมพ์จริง หน้าสุทธิ จำนวนเครื่อง หน้าต่อเครื่อง และค่าใช้จ่ายต่อเครื่อง
  - กราฟยอดย้อนหลังรายเดือนและการแยกข้อมูลตามฝ่าย แผนก สัญญา อาคาร เครื่อง หรือปีงบ
  - ตารางครบทุกกลุ่มในขอบเขต พร้อมค้นหา เรียง และเปิดรายละเอียดระดับเครื่อง/เดือน
  - Excel และ CSV ที่ใช้ตัวกรองและข้อมูลเดียวกับหน้าจอ
  - การเปิดลิงก์ `/compare` เดิมเข้าสู่ Dashboard พร้อมแปลงสถานะที่รองรับ
- **Feature Boundaries:**
  - รวมเฉพาะงานวิเคราะห์จาก Dashboard, Compare และรายงานตามฝ่าย/แผนก
  - รายงานตามสัญญาสำหรับตรวจใบแจ้งหนี้ยังเป็นหน้าต่างหาก
  - ไม่เพิ่ม PDF การคาดการณ์อนาคต การผูกบัญชีผู้ใช้กับหน่วยงาน หรือการเปลี่ยนหน้าบันทึกยอด/ทะเบียนเครื่อง
  - ไม่เปลี่ยน schema หรือ migration ในขอบเขตนี้ หากข้อมูลเดิมไม่พอให้หยุดขออนุมัติแยก
- **User Scenarios:**
  - หัวหน้าหน่วยงานเลือกหลายแผนกข้ามฝ่าย แล้วเทียบยอดพิมพ์และค่าใช้จ่ายในช่วงเดือนเดียวกัน
  - เลือกสัญญาหลายฉบับ แล้วดูยอดย้อนหลังโดยใช้สัญญาที่มีผลจริงในแต่ละเดือน
  - เรียงเครื่องจากใช้มากไปน้อยหรือใช้น้อยไปมาก แล้วเปิดดูยอดรายเดือนของเครื่องนั้น
  - ส่งออก Excel สำหรับรายงานสรุป และ CSV สำหรับคำนวณต่อ โดยได้ข้อมูลตรงกับหน้าจอ

### Detailed Requirements

- **Input:**
  - ปีงบที่เลือกจากบริบทกลางของระบบ
  - เดือนตั้งแต่หนึ่งเดือน หลายเดือนต่อเนื่อง หลายเดือนที่ไม่ต่อเนื่อง หรือทั้งปีงบ
  - รหัสฝ่าย แผนก สัญญา อาคาร และเครื่องแบบหลายค่า
  - มิติที่ใช้แยกข้อมูล ข้อมูลที่แสดง คำค้น และทิศทางเรียง
- **Output:**
  - KPI กราฟ ตาราง และรายละเอียดจากแถวรายเครื่องรายเดือนชุดเดียวกัน
  - สถานะราคาและความครบถ้วนกำกับทุกข้อสรุปที่อาจไม่สมบูรณ์
  - Excel และ CSV ตามขอบเขตเดียวกับหน้าจอ
- **User Interaction:**
  1. เปิดหน้าแล้วเห็นทั้งองค์กรในปีงบที่เลือกโดยมีคำอธิบายขอบเขตชัดเจน
  2. เปลี่ยนช่วงเวลาและตัวกรองกลาง ตัวเลขทุกส่วนอัปเดตพร้อมกัน
  3. เลือก “แยกข้อมูลตาม” และ “ข้อมูลที่แสดง” เพื่อเปลี่ยนกราฟและตาราง
  4. ค้นหา/เรียงตารางและเปิดรายละเอียดของรายการโดยคงตัวกรองเดิม
  5. ส่งออก Excel หรือ CSV จากสถานะเดียวกับหน้าจอ
- **Data Requirements:**
  - เดือนเก็บและกรองเป็น ค.ศ. แต่แสดงผลเป็น พ.ศ. ผ่าน `packages/domain`
  - ปีงบใช้ ต.ค.–ก.ย. ตาม ADR-0001
  - หน่วยงานและสถานที่ย้อนหลังมาจาก `device_location_history` ที่มีผลในเดือนนั้น
  - สัญญาและราคามาจาก `device_contract_history` และช่วงราคาที่มีผลตาม ADR-0019
  - `NULL` ของราคาแปลว่า “ยังยืนยันราคาไม่ได้” ไม่ใช่ศูนย์บาท
  - เงินรวมผ่านหน่วยสตางค์ และไม่คำนวณราคาหรือส่วนลดซ้ำที่เว็บ
  - ค่าเฉลี่ยต่อเครื่องใช้จำนวนเครื่องที่มีแถวข้อมูลในขอบเขต และแสดงชื่อนิยามกำกับ
- **Edge Cases:**
  - ไม่มีข้อมูลในช่วงที่เลือก ให้แสดง empty state พร้อมขอบเขตที่เลือก
  - มีแต่รายการที่ยังไม่ยืนยันราคา ให้ยอดเงินเป็นขีดและแสดงจำนวนรายการรอราคา
  - กลุ่มต่างกันด้านจำนวนเครื่อง ให้แสดงจำนวนเครื่องคู่กับยอดรวม
  - แผนกหรือเครื่องไม่มีสังกัด ให้รวมในกลุ่ม “ไม่ได้ระบุ” และยังเลือก/ส่งออกได้
  - URL มีค่าซ้ำ ค่าไม่รู้จัก หรือเกินขีดจำกัด ให้ normalize เป็นค่าที่หน้าจอใช้จริง
  - เดือนที่บันทึกศูนย์ยังถือว่ามีข้อมูล ส่วนเดือนที่ไม่มีแถวไม่ถูกแปลงเป็นศูนย์

## Design Decisions

### Technical Approach

- **Architecture Choice:** ใช้ `/api/dashboard/monthly-kpi` เป็นแถววิเคราะห์รายเครื่องรายเดือน แล้วรวมและกรองผ่านแบบจำลองรายงานเดียวในเว็บ; endpoint สรุปใช้เฉพาะบริบทที่ต้องคำนวณฝั่งฐานข้อมูล เช่น coverage และงานค้าง
- **Filter Contract:** ขยาย query validation ให้รับรายการรหัสหลายค่าแบบ allow-list และใช้ effective location/contract ใน SQL ทุกเส้นทางที่ตอบข้อมูลย้อนหลัง
- **UI Structure:** ขอบเขต → สรุป → กราฟ/ตาราง → รายละเอียด ใช้ component ใน `ui/` และ semantic tokens ตาม ADR-0008
- **State:** เก็บตัวกรองที่แชร์ได้ใน URL; ค่าการค้นหา/เรียงที่ไม่จำเป็นต่อการแชร์เก็บเป็น state ของหน้า
- **Compatibility:** route `/compare` แปลง query เดิมไปเป็น query ของ Dashboard; ลิงก์ที่แปลงไม่ได้เปิดค่าเริ่มต้นพร้อมคำอธิบาย ไม่เดาตัวเลือกเงียบๆ
- **Exports:** Excel ใช้ model เดียวกับจอและเพิ่มแผ่นคุณภาพข้อมูล; CSV ส่งแถวรายละเอียดที่ผ่านตัวกรองกลางและคำค้นที่แสดงอยู่

### Constraints

- **Performance:** ไม่เพิ่มการขอข้อมูลซ้ำระหว่างกราฟ ตาราง และ export; ใช้ TanStack Query key ที่รวมตัวกรองอย่าง deterministic; ตารางรองรับข้อมูลทั้งหมดด้วย pagination/virtualization ตามปริมาณจริง
- **Compatibility:** Vue 3, Vite, Express CommonJS, MySQL/MariaDB และรูปแบบ API ปัจจุบัน
- **Security:** ทุก endpoint อ่านข้อมูลต้องผ่าน `requireAuth`, `validate`, `asyncHandler` และ cache policy เดิม ไม่มีทางเขียนข้อมูลใหม่
- **Accessibility:** ใช้งานด้วยคีย์บอร์ด มีชื่อควบคุมภาษาไทย อ่านที่ zoom 200% และไม่ใช้สีเพียงอย่างเดียวในการสื่อความหมาย
- **Localization:** flow นี้ใช้คำไทยตรงความหมายและไม่ใช้คำว่า “แนวโน้ม” สำหรับข้อมูลย้อนหลัง

### Risk Assessment

- **Data Scope Risk:** ตัวกรองหลายมิติอาจทำให้ numerator/denominator ของ coverage คนละขอบเขต แก้ด้วย integration test ที่ HTTP API และข้อมูลกรณีหลายอาคาร/หลายหน่วยงาน
- **Historical Accuracy Risk:** การใช้ `devices.contract_id` หรือหน่วยงานปัจจุบันจะย้อนทับอดีต แก้ด้วย shared effective joins และ regression tests
- **Complexity Risk:** รวมหน้าจออาจทำให้หน้าใหญ่เกินไป แก้ด้วย progressive disclosure และมีตัวกรองหลักชุดเดียว
- **Backward Compatibility Risk:** query ของ `/compare` มีหลายรูปแบบ แก้ด้วย mapping test สำหรับ direct URL, back/forward และค่าที่ไม่รู้จัก
- **Export Drift Risk:** ไฟล์อาจไม่ตรงหน้าจอ แก้ด้วย model เดียวกันและ tests ที่อ่าน workbook/CSV กลับมาตรวจ

## Acceptance Criteria

### Functional Acceptance

- [ ] ตัวกรองทุกตัวควบคุม KPI กราฟ ตาราง รายละเอียด Excel และ CSV ด้วยขอบเขตเดียวกัน
- [ ] เลือกหลายฝ่าย หลายแผนกข้ามฝ่าย หลายสัญญา หลายอาคาร และหลายเครื่องได้
- [ ] สัญญา หน่วยงาน และสถานที่ของรายงานย้อนหลังอิงค่าที่มีผลจริงในเดือนนั้น
- [ ] ค่าเริ่มต้นแสดงทุกหน่วยงานและไม่เลือกรายการยอดสูงสุดให้อัตโนมัติ
- [ ] KPI แสดงค่าใช้จ่ายที่ยืนยันแล้ว ยอดพิมพ์จริง หน้าสุทธิ จำนวนเครื่อง หน้าต่อเครื่อง ค่าใช้จ่ายต่อเครื่อง และสถานะข้อมูล
- [ ] แยกข้อมูลตามฝ่าย แผนก สัญญา อาคาร เครื่อง หรือปีงบได้จากพื้นที่เดียว
- [ ] ตารางแสดงทุกกลุ่มในขอบเขต ค้นหาและเรียงสองทิศทางได้
- [ ] เปิดรายละเอียดถึงระดับเครื่องและเดือนโดยคงตัวกรองเดิม
- [ ] `/compare` เดิมเปิด Dashboard ด้วยสถานะเทียบเท่าที่รองรับ
- [ ] Excel มีสรุป รายเดือน เปรียบเทียบ รายละเอียด คุณภาพข้อมูล และเงื่อนไขรายงาน
- [ ] CSV มีข้อมูลรายละเอียดตามตัวกรองและคำค้นที่ใช้อยู่
- [ ] ไม่มีคำว่า “แนวโน้ม” ใน flow วิเคราะห์และไม่มีข้อความสื่อว่าเป็นการคาดการณ์

### Quality Standards

- [ ] Regression tests ครอบ filter contract, effective contract/location, URL state, aggregation และ exports
- [ ] `npm test`, `npm run build`, fixture E2E และ `npm run verify:db` ผ่านโดยไม่มี skip ที่ซ่อน failure
- [ ] `git diff --check` ผ่านและทุกไฟล์ผ่าน review ด้าน Standards, Spec และ Security/robustness
- [ ] ไม่มี schema, migration, auth หรือ production change ใน diff

### User Acceptance

- [ ] หัวหน้าหน่วยงานระบุยอดมาก/น้อยทั้งยอดรวมและต่อเครื่องได้จากหน้าเดียว
- [ ] ผู้ใช้เห็นขอบเขตข้อมูลและสถานะราคาก่อนนำตัวเลขไปตัดสินใจ
- [ ] ตรวจ desktop/mobile, light/dark, keyboard, ข้อความยาว และ zoom 200%
- [ ] เอกสาร Dashboard และ workflow ส่งออกรายงานตรงกับพฤติกรรมสุดท้าย

## Execution Phases

### Phase 1: Data Contract

- [ ] เพิ่ม regression tests ที่ seam ของ HTTP API และ report model
- [ ] ทำตัวกรองหลายค่าและ effective contract/location ให้เป็นสัญญากลาง
- **Deliverables:** filter contract, API tests, data model tests

### Phase 2: Decision Dashboard

- [ ] สร้างตัวกรองกลางและ KPI สำหรับหัวหน้าหน่วยงาน
- [ ] รวมกราฟ ตาราง และรายละเอียดให้ใช้ model เดียวกัน
- [ ] เปลี่ยนคำและลำดับข้อมูลตาม UX ที่ตกลง
- **Deliverables:** Dashboard ใหม่และ component tests

### Phase 3: Consolidation and Export

- [ ] map `/compare` เดิมเข้าหน้า Dashboard
- [ ] ย้าย flow วิเคราะห์ตามฝ่าย/แผนกโดยคงหน้าตรวจสัญญา
- [ ] ทำ Excel และ CSV ตามขอบเขตเดียวกับหน้าจอ
- **Deliverables:** route compatibility, Excel/CSV tests, navigation update

### Phase 4: Verification and Handoff

- [ ] รัน targeted, workspace, build, fixture E2E และ isolated DB checks
- [ ] ตรวจภาพและ accessibility ตาม acceptance criteria
- [ ] รีวิว Standards, Spec และ Security/robustness แล้วปิด findings
- **Deliverables:** evidence, screenshots, review disposition และ human handoff
