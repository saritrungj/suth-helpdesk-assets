# 0028 — บันทึกการนำเข้าแบบคำนวณก่อน แล้วเขียนผลใน transaction เดียวที่สั้น

**สถานะ:** Accepted — ผู้ใช้อนุมัติแผนเมื่อ 2026-09-23 (#178)

## บริบท

ผู้ใช้กำหนดสองข้อที่ดึงกันอยู่: ผู้ใช้ต้องเห็นการนำเข้า **ทั้งหมดหรือไม่เห็นเลย** และห้ามพึ่ง transaction ขนาดใหญ่มาก
ก้อนเดียว ต้องขยายไปประมวลผลเป็นช่วงได้เมื่อข้อมูลโต

ไฟล์จริงวันนี้ (สองสัญญา) = เครื่อง ~500 ยอด ~2,300 แถว commit เดิมของทะเบียนวางแผนใหม่ใน transaction แล้วเขียน
ใช้ ~5 วินาทีกับไฟล์ SUTH192 (log production 2026-09-23)

## การตัดสินใจ

แยกงานหนักออกจากช่วงที่ถือ lock

1. **ตรวจ (`validating`) ทำนอก transaction ที่ commit** — อ่านไฟล์ วางแผนชื่อ/รุ่น/สัญญา จับคู่ยอด เทียบราคา และเทียบ
   ยอดตามใบแจ้งหนี้กับไฟล์ แล้ว **ลองเขียนจริงใน transaction ที่ย้อนกลับเสมอ** (แบบเดียวกับ preview ของยอดมิเตอร์เดิม)
   ตัวเลขที่ผู้ใช้เห็นก่อนบันทึกจึงมาจากเส้นทางเขียนและ view คิดเงินชุดเดียวกับของจริง เก็บ **ลายนิ้วมือ** ของผลตรวจ
   (ไฟล์ + การตัดสินใจ + แผน + ค่าเดิมที่จะถูกเขียนทับ)
2. **บันทึก (`processing`) คือ transaction เดียวที่เขียนแผนที่ตรวจแล้ว** — คำนวณแผนซ้ำจากข้อมูลปัจจุบันภายใน transaction
   (เร็วเพราะไม่มีการอ่านไฟล์หรือ I/O นอกฐาน) เทียบลายนิ้วมือ ไม่ตรง = มีคนแก้ข้อมูลระหว่างนั้น → ย้อนกลับ session กลับไป
   `draft` ให้ตรวจใหม่ ไม่เขียนทับค่าที่ผู้ใช้ไม่เคยเห็น คำสั่งเขียนแบ่งเป็นก้อนละไม่เกิน 500 แถว
3. **หนึ่ง commit ต่อครั้งทั้งระบบ** — `GET_LOCK('suth_import_commit')` กันสอง session เขียนเครื่องชุดเดียวกันพร้อมกัน
   และการเปลี่ยน `ready → processing` เป็น UPDATE แบบมีเงื่อนไข กันกดบันทึกซ้ำ
4. **แผนถูกจัดเป็นหน่วย** (ทะเบียนเครื่อง แล้วยอดทีละงวด) วันนี้ทุกหน่วยอยู่ใน transaction เดียว

## ทางขยายเมื่อข้อมูลโต (ยังไม่ทำ)

เมื่อ commit หนึ่งครั้งเกิน ~10 วินาที หรือเกิน 20,000 แถวยอด ให้บันทึก **ทีละหน่วย** (ทะเบียนก่อน แล้วทีละงวด) แต่ละหน่วย
เป็น transaction ของตัวเอง — การมองเห็นเป็น "ทั้งงวดหรือไม่เห็นเลย" แทน "ทั้งไฟล์" และ session แสดงความคืบหน้ารายหน่วย
หน่วยที่ล้มทำต่อได้จากหน่วยนั้น ต้องเขียน ADR ใหม่เมื่อถึงจุดนั้น เพราะเปลี่ยนความหมายของ "ทั้งหมดหรือไม่เห็นเลย"

## ทางเลือกที่ไม่เลือก

- **เขียนเป็นช่วงแล้วซ่อนแถวที่ยังไม่เสร็จด้วยธงสถานะ** — ทุกเส้นทางอ่าน (v_monthly_kpi ความครบถ้วน ทะเบียน รายงาน)
  ต้องกรองธงนี้ ลืมที่เดียวคือยอดเงินผิดหรือข้อมูลครึ่งไฟล์รั่ว และต้องแก้แกนคิดเงินที่ audit ยืนยันแล้วว่าถูก
- **เขียนเป็นช่วงแล้วลบทิ้งเมื่อพัง (compensating)** — ระหว่างประมวลผลผู้ใช้เห็นข้อมูลครึ่งไฟล์ และถ้า API ตายกลางทาง
  ไม่มีใครลบให้
- **ตารางพักข้อมูล (staging) แล้ว INSERT…SELECT** — ต้องเขียนขั้นตอนลงเครื่องใหม่ (ประวัติที่ตั้ง สถานะการติดตั้ง ช่วงคิดเงิน
  มิเตอร์) เป็น SQL ชุดที่สอง ซ้ำกับของฟอร์มเพิ่มเครื่องแล้วรอวันไม่ตรงกัน

## ผลที่ตามมา

- ช่วงที่ถือ lock ของไฟล์ขนาดวันนี้คือไม่กี่วินาที ต้องวัดซ้ำในเทส E2E ของไฟล์จริงทุกครั้งที่แก้ตัวนำเข้า
- การตรวจลองเขียนแล้วย้อนกลับ จึงต้องมีสิทธิ์เขียนตาราง เหมือน preview ของยอดมิเตอร์เดิม
