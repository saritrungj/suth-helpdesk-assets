# 0027 — งานนำเข้าไฟล์เป็น session ฝั่งเซิร์ฟเวอร์ที่มีวงจรชีวิตและประวัติ

**สถานะ:** Accepted — ผู้ใช้อนุมัติแผนเมื่อ 2026-09-23 (#178)

## บริบท

audit 2026-09-23 พบว่าผู้ใช้ลงทะเบียนเครื่อง 494 เครื่องจากรายงานมิเตอร์ แต่ยอดพิมพ์เป็นศูนย์ — ไฟล์เดียวต้อง
อัปโหลดสองที่ (หน้าเพิ่มเครื่อง แล้วไอคอนในหน้าบันทึกยอด) และหน้านำเข้าเก็บไฟล์กับการตัดสินใจไว้ใน component
ทำตามคำเตือน "สร้างสัญญาก่อน" แล้วกลับมา ไฟล์และทุกการตัดสินใจหาย และไม่มีที่ไหนตอบได้ว่ายอดชุดหนึ่งมาจากไฟล์ไหน
ใครนำเข้า

## การตัดสินใจ

- **หนึ่งไฟล์ = หนึ่ง import session เก็บในฐานข้อมูล** (`import_session`) ไฟล์ต้นฉบับเก็บบนดิสก์ของ API
  (`IMPORT_SESSION_DIR` ค่าเริ่มต้น `uploads/import-sessions/`) พร้อม sha256 การตัดสินใจ ผลตรวจล่าสุด และผลการบันทึก
  อยู่ในแถวเดียวกัน ออกจากหน้า รีเฟรช หรือไปทำต่อที่เครื่องอื่นได้ เพราะไม่มีอะไรอยู่ในเบราว์เซอร์
- **สถานะ**

  | สถานะ | ความหมาย | ไปต่อได้ที่ |
  |---|---|---|
  | `draft` | อัปโหลดแล้ว ยังมีสิ่งที่ต้องตัดสินหรือเงื่อนไขที่ขาด | validating, expired |
  | `validating` | กำลังตรวจ (ชั่วคราว) | draft, ready, failed |
  | `ready` | ตรวจผ่าน บันทึกได้ | validating, processing, expired |
  | `processing` | กำลังบันทึก (ชั่วคราว) | completed, failed, draft (ข้อมูลเปลี่ยนระหว่างตรวจ) |
  | `completed` | บันทึกแล้ว — จบ | — |
  | `failed` | ตรวจหรือบันทึกล้มด้วยเหตุที่ไม่คาด เก็บ error ไว้ ลองใหม่ได้ | validating, expired |
  | `expired` | ไม่มีการเคลื่อนไหว 14 วัน หรือผู้ดูแลยกเลิก — จบ | — |

  การแก้การตัดสินใจทุกครั้งพาไป `validating` ใหม่เสมอ สถานะ `ready` จึงหมายถึง "ผลตรวจล่าสุดตรงกับการตัดสินใจล่าสุด"
  ชั่วคราวที่ค้างเกิน 15 นาที (API ตายกลางทาง) ถือเป็น `failed` เมื่อมีคนเปิดดู
- **หมดอายุแทนการลบ** — `draft` / `ready` / `failed` ที่ไม่มีการเคลื่อนไหว 14 วันกลายเป็น `expired` เมื่อมีคนเปิดรายการ
  (ไม่มีงานเบื้องหลัง) แถว session ประวัติ และไฟล์ยังอยู่ การล้างไฟล์เก่าเป็นงานภายหลังที่ต้องขออนุมัติแยก
- **ประวัติแบบเพิ่มอย่างเดียว** (`import_session_event`) — อัปโหลด ผลตรวจ การตัดสินใจที่เปลี่ยน สัญญา/ปีงบที่สร้างจาก
  หน้านำเข้า เริ่มบันทึก ผลการบันทึก ข้อผิดพลาด หมดอายุ ทุกแถวมีผู้กระทำและเวลา ไม่มี API แก้หรือลบ
- **ที่มาของข้อมูล** — `devices.import_session_id` = session ที่สร้างเครื่อง, `print_transactions.import_session_id` =
  session ที่เขียนค่าปัจจุบัน การแก้ยอดด้วยมือที่เปลี่ยนจำนวนหน้าล้างค่านี้ (แบบเดียวกับเลขมิเตอร์ #143) จึงตอบได้ว่ายอด
  ตัวนี้มาจากไฟล์ไหน ใครนำเข้า เมื่อไร หรือถูกแก้มือทีหลัง
- endpoint เดิม `POST /devices/import` และ `POST /print-transactions/import` ยังอยู่และตอบเหมือนเดิม (สคริปต์และเทส
  — **ถอดออกแล้วใน #192**: งานนำเข้าเป็นทางเดียว เส้นทางเดิมเขียนยอดโดยไม่มีที่มาและประวัติ
  ใช้อยู่) ทั้งสองทางเรียกตรรกะชุดเดียวกัน

## ทางเลือกที่ไม่เลือก

- **เก็บความคืบหน้าใน sessionStorage/IndexedDB** — ไฟล์หลาย MB การตัดสินใจผูกกับข้อมูลบนเซิร์ฟเวอร์ ไม่รอดการเปลี่ยนเครื่อง
  และไม่มีประวัติให้ตรวจ (ใช้กับฟอร์มเล็กๆ แทน — #177)
- **เก็บไฟล์เป็น BLOB ในฐาน** — ทำให้ backup รายวันโตตามไฟล์ที่ไม่ใช่ข้อมูลธุรกิจ และ dump/restore ช้าลง
- **ลบ session เมื่อหมดอายุ** — ผู้ใช้ต้องการคำตอบว่า "ใครนำเข้าและเกิดอะไรขึ้น" ย้อนหลังได้เสมอ

## ผลที่ตามมา

- migration ใหม่ `migration_add_import_sessions.sql` และ schema-check ตรวจตารางใหม่
- ดิสก์ของเครื่อง API ต้องมีที่สำหรับไฟล์นำเข้า (ไฟล์ละไม่เกิน 5 MB) และไม่อยู่ใน backup ฐานข้อมูล
- กลยุทธ์การบันทึกอยู่ใน [ADR-0028](0028-import-commit-strategy.md) สิทธิ์อยู่ใน [ADR-0029](0029-import-session-visibility.md)
