# 0032 — ฐานพัฒนาแยกจากฐานจริง ใช้ข้อมูลตัวอย่าง และใช้รหัสคนละชุด

- สถานะ: Accepted — ผู้ใช้เลือก "ฐาน dev เป็นข้อมูลตัวอย่าง" เมื่อ 2026-09-24
- Issue: #194 · แก้ข้อ "ฐานเดียว" ของ [ADR-0024](0024-docker-development-database.md)

## บริบท

ADR-0024 ให้ `hospital_it_asset` บน Docker เป็นข้อมูลจริงฐานเดียว และเลือกไม่แยกฐานพัฒนา เพราะผู้ใช้ไม่ต้องการข้อมูลจำลอง
และสองฐานบนเครื่องเดียวเคยทำให้ข้อมูลปนกัน

ตั้งแต่นั้น production (`D:\suth-prod`) ขึ้นบนเครื่องเดียวกันและใช้ฐานนั้น ส่วนตัวพัฒนา (API :3000 / เว็บ :5173 จาก checkout หลัก)
ก็ยังชี้ฐานเดียวกัน ผู้ใช้เคยนำเข้าไฟล์ผ่านหน้าเก่าของตัวพัฒนาโดยเข้าใจว่าเป็นระบบจริง และเทสหรือ agent ที่รันบนตัวพัฒนา
เขียนข้อมูลคิดเงินจริงได้ ความเสี่ยงนี้ใหญ่กว่าเหตุผลเดิม

## การตัดสินใจ

- บริการ `db-dev` ใน `compose.yaml` (profile `dev`): MySQL รุ่นเดียวกัน พอร์ต `127.0.0.1:3308` volume `mysql-dev-data`
  สร้างจาก `schema.sql` + `seed_ci.sql` (ข้อมูลตัวอย่างชุดเดียวกับ `verify:db` มีเคสร้ายจงใจ ปีงบคำนวณจากวันที่สร้างฐาน)
- **รหัสคนละชุด** (`SUTH_DEV_*` ใน `compose.env`) — `apps/api/.env` ของเครื่องพัฒนาถือรหัสของฐานพัฒนาเท่านั้น
  ถ้าตั้งพอร์ตผิดไปชี้ฐานจริง การต่อจะล้มเพราะรหัสไม่ตรง ไม่ใช่เขียนลงข้อมูลจริงเงียบๆ
- `npm run db:up` ยังเปิดเฉพาะฐานจริงเหมือนเดิม ฐานพัฒนาใช้ `db:dev:up` / `db:dev:down` / `db:dev:reset` / `db:dev:bootstrap`
- ฐานจริงยังเป็นไปตาม ADR-0024 ทุกข้อ: ไม่มีข้อมูลจำลอง ข้อมูลเข้าผ่าน API เท่านั้น — ตอนนี้ผู้ใช้คือ production

## ทางเลือกที่ไม่เลือก

- **สำเนาข้อมูลจริงเป็นฐานพัฒนา** — ข้อมูลของหน่วยงานไปอยู่ในที่ที่ agent ทดสอบเขียนได้ ผู้ใช้เลือกข้อมูลตัวอย่าง
- **ใช้รหัสชุดเดียวกัน** — ง่ายกว่า แต่ `.env` ที่ชี้พอร์ตผิดจะเขียนลงฐานจริงสำเร็จ ซึ่งคือปัญหาที่ต้องการกัน
- **ใช้ `seed_dummy_data.sql`** — เดือนตัวอย่างตรึงไว้ปี 2025 ไม่อยู่ในปีงบที่ seed ไว้ รายงานส่วนใหญ่จึงว่าง

## ผลที่ตามมา

- เครื่องพัฒนาต้องตั้ง `SUTH_DEV_*` ใน `compose.env` และเปลี่ยน `apps/api/.env` เป็นพอร์ต 3308 ครั้งเดียว
- ข้อมูลบนฐานพัฒนาทิ้งได้เสมอ (`db:dev:reset`) — ไม่ต้องคืนค่าหลังทดสอบแบบที่ฐานจริงต้องทำ
