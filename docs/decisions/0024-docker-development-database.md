# 0024 — ฐานข้อมูลบน Docker Compose ด้วย MySQL 8.4 LTS ฐานเดียวที่เป็นข้อมูลจริง

**สถานะ:** Accepted — ผู้ใช้อนุมัติเมื่อ 2026-09-22 (#130) ขยายขอบเขตข้อยกเว้น bootstrap ของ [ADR-0016](0016-isolated-qa-database-and-bootstrap-harness.md) ให้ครอบฐานบน Docker และเปลี่ยน engine ที่ [ADR-0005](0005-database-engine.md) ตั้งไว้ (MariaDB) เป็น MySQL

## บริบท

ฐานบนเครื่องพัฒนาเป็น MariaDB 10.4 จาก XAMPP ซึ่งหมดระยะซัพพอร์ตตั้งแต่ 18 มิ.ย. 2024 ([MariaDB maintenance policy](https://mariadb.org/about/#maintenance-policy)) บนเครื่องมีฐานสิบกว่าชุดปนกันระหว่างข้อมูลจริง ข้อมูลจำลอง และฐานทดลอง ตั้งฐานใหม่ต้องทำมือหลายขั้น และเปิดดูข้อมูลได้ทางเดียวคือ phpMyAdmin ของ XAMPP ด้วยบัญชี root ซึ่งแก้ข้อมูลได้ทุกอย่าง

`npm run verify:db` ใช้ container `mysql:8.4` ชั่วคราวอยู่แล้ว แต่ลบทิ้งทุกรอบ

ผู้ใช้ตัดสินสองข้อ: ใช้ MySQL 8.4 และ "ไม่ทดลองกับข้อมูลปลอมอีกแล้ว" — ฐานที่ระบบใช้ต้องมีแต่ข้อมูลจริง

## การตัดสินใจ

- `compose.yaml` ที่รากของ repo มีสองบริการ: `db` (`mysql:8.4` — LTS, premier support ถึง เม.ย. 2029 และ extended ถึง เม.ย. 2032 ตาม [endoflife.date](https://endoflife.date/mysql)) และ `phpmyadmin`
- เลือก 8.4 ไม่ใช่ 9.7 LTS (ออก เม.ย. 2026) เพราะเป็นรุ่นเดียวกับ `verify:db` ที่ผ่านชุดทดสอบ E2E ทั้งหมดแล้ว และใช้งานจริงมาสองปี
- **ฐานเดียว `hospital_it_asset` คือข้อมูลจริง** ลงจากไฟล์ของหน่วยงานผ่าน HTTP API เท่านั้น ไม่มี seed ข้อมูลจำลองบนฐานนี้ ข้อมูลจำลองมีได้เฉพาะใน container ชั่วคราวของชุดทดสอบที่ลบทิ้งทุกรอบ
- ทุกพอร์ตผูก `127.0.0.1` เท่านั้น เครื่องต่อเครือข่ายโรงพยาบาล
- ฐานใหม่โหลด `database/schema.sql` อัตโนมัติ และสร้างบัญชีสองชุด:
  - บัญชีแอป — `SELECT/INSERT/UPDATE/DELETE` และ `SHOW VIEW` (ตัวตรวจ schema ตอนบูตอ่านนิยาม view) ไม่มีสิทธิ์สร้างหรือแก้ตาราง
  - บัญชีอ่านอย่างเดียว — `SELECT` และ `SHOW VIEW` สำหรับ phpMyAdmin / DBeaver ดูได้ว่าข้อมูลเข้าหรือยัง แต่แก้ไม่ได้
- phpMyAdmin ยอมให้เข้าเฉพาะบัญชีอ่านอย่างเดียว (`AllowRoot = false` + `AllowDeny`) — root และบัญชีแอปถูกปฏิเสธแม้รหัสถูก งานดูแลฐานที่ต้องใช้ root ทำผ่าน `docker exec`
- `npm run db:bootstrap` ต่อฐานตรงเพื่อตั้งรหัส `admin` และลบบัญชี prototype `user1` เท่านั้น ทำงานเฉพาะฐานที่ยังเป็นบัญชี prototype ล้วน — ขอบเขตเดียวกับข้อ 3 ของ ADR-0016
- รหัสผ่านทั้งหมดอยู่ใน `database/docker/compose.env` ซึ่งอยู่ใน `.gitignore`
- ย้ายข้อมูลข้ามเครื่องด้วย `npm run db:dump` / `db:restore` (ไฟล์ `mysqldump` ธรรมดา) ไม่ย้าย Docker volume ตรงๆ เพราะไฟล์ SQL อ่านได้ ตรวจได้ และ restore สำรองของเดิมก่อนเสมอ
- ไฟล์จริงของหน่วยงาน (Excel ต้นฉบับ plan ข้อมูลหลัก ไฟล์สำรอง) เก็บนอก repo เช่น `D:\suth-data\` เพราะ repo เป็น public — `.gitignore` กันไฟล์ Excel/CSV ทุกไฟล์ใต้ `docs/`

## ทางเลือกที่ไม่เลือก

- **อยู่กับ MariaDB ตาม ADR-0005** — ผู้ใช้เลือก MySQL 8.4 และทำให้เครื่องพัฒนากับ `verify:db` เป็น engine เดียวกัน ข้อที่ต้องยอมรับคือ ADR-0005 ให้เหตุผลว่าฝ่าย IT ดูแล MariaDB เป็นอยู่แล้ว — ก่อนขึ้น production ต้องยืนยันกับฝ่าย IT ว่ารับดูแล MySQL 8.4 ได้
- **MySQL 9.7 LTS** — ซัพพอร์ตยาวกว่า (ถึง 2037) แต่เพิ่งออก ต้องย้ายชุดทดสอบตามไปด้วย ขยับได้ภายหลังเมื่อผู้ใช้ต้องการ
- **สองฐาน: ข้อมูลจริงกับข้อมูลจำลองสำหรับพัฒนา** — ผู้ใช้ไม่ต้องการข้อมูลจำลองอีก และสองฐานบนเครื่องเดียวคือจุดที่ข้อมูลเคยปนกันมาแล้ว
- **อัป XAMPP เป็นรุ่นใหม่** — ยังเป็นการติดตั้งมือบนเครื่องเดียว ตั้งใหม่ซ้ำไม่ได้
- **ให้ phpMyAdmin ใช้ root ตามค่าเริ่มต้น** — เปิดทางเข้าที่สองที่แก้ข้อมูลได้โดยไม่ผ่านกฎสิทธิ์และไม่เกิดประวัติ ซึ่ง AGENTS.md ห้าม

## ผลที่ตามมา

- **ห้ามรันชุดทดสอบที่เขียนข้อมูล (live-write E2E, seed) กับ API ที่ต่อฐานนี้** ชุดทดสอบที่ต้องเขียนใช้ `npm run verify:db` ซึ่งสร้างฐานชั่วคราวแยกเอง
- client ของ image MySQL โหลดไฟล์ SQL ด้วย latin1 เป็นค่าเริ่มต้น ชื่อไทยใน `schema.sql` ถูกเข้ารหัสซ้อนลงฐานโดยไม่มี error (พบระหว่างย้าย) — ไฟล์ SQL ของ repo จึงขึ้นต้นด้วย `SET NAMES utf8mb4;` เสมอ ไม่พึ่ง charset ของ client
- MySQL 8.4 ใช้ `sql_mode` แบบ strict ส่วน XAMPP ไม่ strict — ค่าที่ยาวเกินคอลัมน์หรือวันที่ผิดจะ error แทนการตัดทิ้งเงียบ ถ้าพบ ให้แก้ที่ต้นเหตุ ไม่ใช่ปิด strict
- บัญชีที่ไม่มี `SHOW VIEW` ได้นิยาม view ว่าง เดิมถูกรายงานว่าต้องรัน migration ซ้ำ ตอนนี้รายงานเป็นเรื่องสิทธิ์
- entrypoint ของ image ไม่หยุดเมื่อสคริปต์สร้างบัญชีล้ม `db:bootstrap` จึงตรวจว่าบัญชีแอปต่อได้ก่อนทำอย่างอื่น
- ฐาน SUTH ทั้งหมดใน XAMPP ถูกสำรองไว้ที่ `D:\suth-data\backups\xampp-20260922\` แล้วลบ ฐาน QA แยกของ [ADR-0016](0016-isolated-qa-database-and-bootstrap-harness.md) (`hospital_it_asset_qa48`) ก็ถูกลบด้วย ถ้าจะใช้ harness นั้นอีกต้องตั้งฐานใหม่บน container แยก ห้ามชี้มาที่ฐานนี้
