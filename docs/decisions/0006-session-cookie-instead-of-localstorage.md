# 0006 — เก็บ token ของ session ใน cookie แบบ httpOnly ไม่ใช่ localStorage

**สถานะ:** Accepted

## บริบท

เดิม `POST /api/auth/login` ส่ง JWT กลับมาใน response body แล้วเว็บเก็บไว้ใน `localStorage` และแนบเป็น `Authorization: Bearer` เองทุก request

ปัญหาสองข้อ:

1. **JavaScript ทุกตัวในหน้าอ่าน token ได้** ถ้ามีช่องโหว่ XSS สักจุด ผู้โจมตีขโมย token ไปใช้ต่อได้ทันที ระบบนี้รับไฟล์ Excel/CSV จากภายนอกมาแสดงผล จึงมีพื้นผิวให้ XSS เกิดได้จริง
2. **ยกเลิก token ก่อนหมดอายุไม่ได้** token มีอายุ 8 ชั่วโมง ถ้าหลุดออกไปก็ใช้ได้จนครบ ไม่มีปุ่มไหนหยุดได้

## การตัดสินใจ

ย้าย token ไปอยู่ใน cookie ชื่อ `suth_session` ที่ตั้ง `httpOnly` — JavaScript อ่านไม่ได้เลย เบราว์เซอร์แนบไปให้เองทุก request

| ค่า | ตั้งเป็น | เหตุผล |
|---|---|---|
| `httpOnly` | `true` | JavaScript อ่านไม่ได้ ปิดช่องทาง XSS ขโมย token |
| `sameSite` | `lax` (ปรับผ่าน `COOKIE_SAMESITE`) | เว็บกับ API อยู่โดเมนเดียวกัน (ต่างพอร์ต/subdomain ยังนับว่าเดียวกัน) ถ้าคนละโดเมนจริงต้องใช้ `none` |
| `secure` | `true` เมื่อ `NODE_ENV=production` หรือ `sameSite=none` | เบราว์เซอร์บังคับว่า `sameSite=none` ต้องมาคู่กับ `secure` |
| `maxAge` | 8 ชั่วโมง | เท่าอายุ JWT เดิม |

เพิ่มสอง endpoint ที่จำเป็นตามมา:

- `GET /api/auth/me` — เว็บอ่าน cookie เองไม่ได้ ตอนเปิดหน้าใหม่จึงต้องถามว่ายังล็อกอินอยู่ไหมและเป็นใคร
- `POST /api/auth/logout` — สั่งลบ cookie ไม่ต้องมี token ที่ยังใช้ได้ก็เรียกได้ ไม่งั้นคนที่ token หมดอายุแล้วจะ logout ไม่ได้และ cookie ค้างในเบราว์เซอร์

`require-auth` อ่าน cookie ก่อน แล้วค่อย fallback ไป `Authorization: Bearer` — header ยังรับอยู่สำหรับ script, curl และการทดสอบที่ไม่มีที่เก็บ cookie ซึ่งไม่เพิ่มความเสี่ยง เพราะความเสี่ยงจริงอยู่ที่ "เว็บเก็บ token ไว้ที่ไหน" ไม่ใช่ที่ API ยอมรับ header

## ทางเลือกที่พิจารณาแล้วไม่เลือก

**เก็บ token ใน memory อย่างเดียว (ไม่ persist)** — ปิดช่อง XSS ได้เหมือนกัน แต่รีเฟรชหน้าทีต้องล็อกอินใหม่ทุกครั้ง ซึ่งผู้ใช้ที่ต้องกรอกยอด 20 เครื่องรับไม่ได้

**เพิ่ม refresh token + revocation list** — แก้เรื่อง revoke ได้ตรงจุดกว่า แต่ต้องมีที่เก็บ state ฝั่งเซิร์ฟเวอร์และโค้ดอีกชุด เกินความจำเป็นของระบบภายในที่มีผู้ใช้หลักสิบคน เก็บไว้พิจารณาเมื่อจำนวนผู้ใช้หรือความต้องการเปลี่ยน

**อยู่กับ localStorage ต่อ** — ไม่ยอมรับ เพราะระบบรับไฟล์จากภายนอกมาแสดงผล และตัวเลขในระบบเป็นงบประมาณ

## ผลที่ตามมา

- **ผู้ใช้ที่ล็อกอินค้างอยู่จะหลุดทั้งหมดตอน deploy** เพราะ token เก่าอยู่ใน localStorage ที่ระบบไม่อ่านแล้ว ต้องล็อกอินใหม่ครั้งเดียว
- `main.js` ต้องเรียก `GET /auth/me` ให้เสร็จ **ก่อน** `app.use(router)` เพราะบรรทัดนั้นเริ่ม navigation แรกซึ่งเรียก router guard ทันที ถ้าสลับลำดับจะเด้งไป `/login` ทุกครั้งที่รีเฟรช
- ถ้าเว็บกับ API อยู่คนละโดเมนตอน deploy ต้องตั้ง `COOKIE_SAMESITE=none` และเสิร์ฟผ่าน HTTPS เท่านั้น
- `CORS_ORIGIN` ต้องระบุ origin ที่แน่นอน ใช้ `*` ไม่ได้ เพราะ cookie ต้องมากับ `credentials: true`
