# 0002 — เก็บเดือนเป็น ค.ศ. รับเข้าได้ทั้ง พ.ศ. และ ค.ศ.

**สถานะ:** Accepted

## บริบท

คอลัมน์ `print_transactions.month` เก็บเดือนเป็นข้อความรูปแบบ `"YYYY-MM"` แต่ไม่เคยมีการระบุว่า `YYYY` เป็นปี พ.ศ. หรือ ค.ศ. และไม่มีอะไรบังคับ

โค้ดทั้งระบบเขียนโดยสมมติว่าเป็น ค.ศ. — [ADR-0001](0001-thai-fiscal-year-oct-sep.md) แปลงปีงบ พ.ศ. เป็นช่วงเดือน ค.ศ. และตัวอ่านไฟล์นำเข้าแปลงหัวคอลัมน์ `meter 9/67` เป็น ค.ศ. ให้แล้ว

แต่ข้อมูลที่ถูกใส่เข้าฐานข้อมูลตรงๆ ผ่าน phpMyAdmin หรือ SQL มือ เป็น พ.ศ. (`"2568-10"` ถึง `"2569-03"`) เมื่อ query กรองด้วยช่วงปีงบจริง (`"2025-10"` ถึง `"2026-09"`) จึงไม่เจอสักแถว หน้าค่าใช้จ่ายและยอดพิมพ์รายเดือนแสดงว่าง ทั้งที่มีข้อมูล 114 แถวอยู่ในตาราง

## การตัดสินใจ

แยกสามชั้นออกจากกันให้ชัด:

| ชั้น | รูปแบบ |
|---|---|
| **รับเข้า** | รับได้ทั้ง พ.ศ. และ ค.ศ. — `2568-10`, `2025-10`, `2568-1`, `2568/10`, `10/2568` |
| **เก็บ** | ค.ศ. `"YYYY-MM"` เท่านั้น |
| **แสดงผล** | พ.ศ. (ฝั่ง frontend บวก 543 เอง) |

การแปลงอยู่ที่ `normalizeMonth()` ใน `backend/utils/month.js` ที่เดียว เส้นแบ่งคือ **ปี ≥ 2400 ถือเป็น พ.ศ.** — ระบบนี้ไม่มีทางมีข้อมูลปี ค.ศ. 2400 และไม่มีทางมีปี พ.ศ. ต่ำกว่า 2400 เส้นนี้จึงไม่กำกวมตลอดอายุการใช้งาน

ฐานข้อมูลบังคับด้วย `CHECK` constraint (`chk_print_transactions_month_ce`) เพื่อให้กฎมีผลกับทุกทางเข้า ไม่ใช่เฉพาะทาง API

## ทางเลือกที่พิจารณาแล้วไม่เลือก

**เก็บทั้ง พ.ศ. และ ค.ศ. ปนกันในคอลัมน์เดียว แล้วแปลงตอน query** — นี่คือสิ่งที่ขอมาตอนแรก แต่ทำไม่ได้อย่างปลอดภัย เพราะ `"2568-10"` กับ `"2025-10"` เป็นเดือนเดียวกันแต่เป็นคนละ string ทำให้ `UNIQUE KEY (device_id, month)` กันข้อมูลซ้ำไม่ได้ ยอดพิมพ์เดือนเดียวกันจะถูกบันทึกสองแถวและถูกนับสองรอบ ค่าใช้จ่ายบานโดยไม่มีอะไรเตือน สำหรับตัวเลขที่เป็นเงินงบประมาณ ความเสี่ยงนี้รับไม่ได้

**เก็บเป็น พ.ศ. ทั้งหมด** — ตรงกับสิ่งที่ผู้ใช้เห็นบนหน้าจอ แต่ต้องแก้ทุกจุดที่คำนวณวันที่ และทำให้ integration กับระบบอื่นในอนาคตยากขึ้น เพราะ `DATE` ทุกชนิดในฐานข้อมูลเป็น ค.ศ. อยู่แล้ว

**เก็บเป็นชนิด `DATE` แทนข้อความ** — ถูกต้องกว่าในเชิงชนิดข้อมูล แต่ต้องแก้ query ทั้งระบบพร้อมกัน เก็บไว้ทำเป็นงานแยกในภายหลัง

## ผลที่ตามมา

- ทุกทางเข้าที่รับเดือนต้องผ่าน `normalizeMonth()` ก่อนเสมอ — route, importer, query parameter
- ฐานข้อมูลที่มีอยู่ต้องรัน `database/migrations/migration_normalize_month_to_ce.sql` ก่อนใช้โค้ดเวอร์ชันนี้ ไม่งั้นหน้าค่าใช้จ่ายจะว่าง
- migration ตัวนั้นจะหยุดและไม่แตะข้อมูล ถ้าพบเครื่องที่มีทั้งแถว พ.ศ. และ ค.ศ. ของเดือนเดียวกัน เพราะกรณีนั้นต้องให้คนตัดสินว่ายอดไหนถูก
- ถ้าเปลี่ยนไปใช้ชนิดวันที่จริงในอนาคต ให้เก็บกฎ "แสดงเป็น พ.ศ." ไว้ที่ชั้นแสดงผลเท่านั้นเหมือนเดิม
