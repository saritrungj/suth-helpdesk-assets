# 0011 — เซิร์ฟเวอร์ MCP แบบอ่านอย่างเดียว

**สถานะ:** Accepted

## บริบท

คำถามที่ผู้บริหารและหัวหน้าฝ่ายถามจริงเกี่ยวกับระบบนี้มีลักษณะเดียวกันเกือบทั้งหมด

- "ไตรมาสที่แล้วแผนกไหนพิมพ์เพิ่มขึ้นมากที่สุด"
- "เครื่องที่ยังไม่ผูกสัญญามีกี่เครื่อง อยู่ตึกไหนบ้าง"
- "ปีนี้ใช้งบไปแล้วเท่าไหร่ เทียบกับปีที่แล้วเป็นยังไง"

ข้อมูลทั้งหมดมีอยู่ในระบบแล้ว แต่การจะตอบต้องเปิดสามหน้า กดตัวกรองห้าครั้ง แล้วเอา
ตัวเลขมาเทียบเอง ซึ่งแปลว่าในทางปฏิบัติไม่มีใครถาม — คนที่อยากรู้ไม่ใช่คนที่ใช้ระบบ
เป็น และคนที่ใช้ระบบเป็นก็ไม่มีเวลามานั่งทำรายงานให้ทุกครั้งที่มีคนสงสัย

Model Context Protocol (MCP) เป็นมาตรฐานที่ผู้ช่วย AI ทุกเจ้ารองรับแล้วในปี 2026
สำหรับต่อเข้ากับข้อมูลและเครื่องมือภายในองค์กร

## การตัดสินใจ

**เพิ่ม `apps/mcp/` เป็นเซิร์ฟเวอร์ MCP แบบ stdio ที่มีแต่เครื่องมืออ่านข้อมูล**

เครื่องมือที่มี

| เครื่องมือ | ตอบคำถามแบบไหน |
|---|---|
| `get_overview` | "ตอนนี้ใช้ไปเท่าไหร่แล้ว มีอะไรค้างบ้าง" |
| `find_devices` | "เครื่อง Canon มีกี่เครื่อง" / "เครื่องที่ยังไม่มีสัญญาอยู่ตึกไหน" |
| `department_usage` | "แผนกไหนใช้เพิ่มขึ้นมากที่สุด" |
| `missing_readings` | "ยังมีเดือนไหนที่ยังไม่ได้กรอก" |
| `contract_summary` | "สัญญาไหนใช้งบมากที่สุด" |

### ข้อจำกัดสองข้อที่ตั้งใจใส่ไว้ และไม่ใช่เพราะทำไม่เสร็จ

**1. ไม่มีเครื่องมือที่เขียนข้อมูลแม้แต่ตัวเดียว**

ข้อมูลขาเข้าของเครื่องมือ MCP มาจากโมเดลภาษา **ไม่ได้มาจากผู้ใช้โดยตรง** ถ้าเปิดให้
เขียนได้ ข้อความที่อยู่ในเอกสาร อีเมล หรือไฟล์ที่โมเดลอ่านเจอระหว่างทาง อาจกลายเป็น
คำสั่งแก้ยอดพิมพ์ได้โดยที่ไม่มีคนกดยืนยัน ซึ่งเป็นรูปแบบการโจมตีที่มีรายงานจริงแล้ว
ในระบบ MCP ที่ใช้งานอยู่ (คำแนะนำด้านความปลอดภัย MCP ปี 2026 ระบุตรงกันว่าให้ถือว่า
ข้อมูลขาเข้าของเครื่องมือเป็นข้อมูลที่เชื่อไม่ได้เสมอ)

ยอดพิมพ์คือฐานของทุกบาทในระบบนี้ การบันทึกจึงยังต้องผ่านหน้าเว็บที่มีคนกดยืนยันเสมอ

**2. เรียกผ่าน HTTP API เดิม ไม่ต่อ MySQL ตรง**

การต่อฐานข้อมูลตรงจะเร็วกว่าและเขียนง่ายกว่า แต่จะสร้าง "ทางเข้าที่สอง" ที่ไม่ผ่าน
ด่านสิทธิ์เดียวกับที่ทุกอย่างผ่าน กฎอย่าง "viewer แก้ข้อมูลไม่ได้" อยู่ในชั้น API
ทั้งหมด การข้ามชั้นนั้นแปลว่าต้องเขียนกฎเดิมซ้ำแล้วรอวันที่มันไม่ตรงกัน

สิทธิ์ของเซิร์ฟเวอร์นี้จึงเท่ากับสิทธิ์ของบัญชีที่ตั้งไว้ใน environment พอดี ไม่มากกว่า
— **แนะนำให้สร้างบัญชีแยกที่มีสิทธิ์ระดับ `viewer` ไว้ให้ตัวนี้โดยเฉพาะ** เพื่อให้
แม้ token หลุดก็ยังอ่านได้อย่างเดียว

### คำตอบเป็นข้อความ ไม่ใช่ JSON ดิบ

คำตอบของเครื่องมือถูกอ่านโดยโมเดลภาษา ตารางข้อความที่มีหน่วยกำกับ (`"85,943.36 บาท"`,
`"เมษายน 2569"`) จึงมีประโยชน์กว่า JSON ดิบ เพราะโมเดลไม่ต้องเดาว่า `12500` คือแผ่น
หรือบาท และไม่ต้องแปลง ค.ศ. เป็น พ.ศ. เอง ซึ่งเดาผิดได้

## ทางเลือกที่พิจารณาแล้วไม่เลือก

**เปิดให้เขียนข้อมูลได้ด้วย แล้วให้ผู้ใช้ยืนยันก่อนทุกครั้ง** — การยืนยันเกิดที่ผู้ช่วย
AI ไม่ใช่ที่ระบบของเรา ระบบเราไม่มีทางรู้ว่ามีคนยืนยันจริงหรือไม่ ในเมื่อสิ่งที่จะถูก
แก้คือฐานของทุกบาทในรายงาน ความเสี่ยงไม่คุ้มกับความสะดวก

**ทำเป็น HTTP MCP server แทน stdio** — จะกลายเป็นบริการที่ต้องเปิดพอร์ต ต้องดูแล
เรื่องสิทธิ์และการเข้าถึงเพิ่มอีกชั้น ในขณะที่ผู้ใช้จริงคือคนไม่กี่คนที่ใช้บนเครื่อง
ตัวเอง stdio จึงพอดีกับความต้องการและไม่เพิ่มพื้นที่ให้ถูกโจมตี

**ไม่ทำเลย ให้ใช้หน้าเว็บอย่างเดียว** — ก็ทำได้ แต่ไม่ได้แก้ปัญหาที่ว่าคนที่อยากรู้
กับคนที่ใช้ระบบเป็นเป็นคนละคนกัน

## ผลที่ตามมา

- เพิ่ม workspace ใหม่ `apps/mcp` พร้อม dependency `@modelcontextprotocol/sdk`
  แยกจาก `apps/api` และ `apps/web` โดยสิ้นเชิง — ไม่ติดตั้งก็ไม่กระทบอะไร
- ต้องมีบัญชีผู้ใช้สำหรับเครื่องมือนี้ ตั้งค่าผ่าน environment (ดู
  `docs/how-to/connect-mcp.md`) **ห้ามเก็บรหัสผ่านไว้ในไฟล์ใน repository**
- คำขอจากเครื่องมือนี้ปรากฏในล็อกของ API เหมือนคำขอจากหน้าเว็บทุกประการ ตรวจสอบ
  ย้อนหลังได้ว่าใครถามอะไรเมื่อไหร่
- **ข้อควรระวัง:** ถ้าวันหลังจะเพิ่มเครื่องมือที่เขียนข้อมูล ต้องกลับมาแก้ ADR ฉบับนี้
  พร้อมเหตุผล ไม่ใช่เพิ่มเงียบๆ — ข้อจำกัดข้อนี้คือสาระสำคัญของการตัดสินใจ ไม่ใช่
  รายละเอียดการติดตั้ง
