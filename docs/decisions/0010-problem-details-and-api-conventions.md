# 0010 — ข้อผิดพลาดแบบ Problem Details และข้อตกลงร่วมของ API

**สถานะ:** Accepted

## บริบท

API เติบโตมาแบบทีละเส้นทาง แต่ละไฟล์เขียนวิธีจัดการเรื่องพื้นฐานเองซ้ำๆ ผลที่ตามมา
ไม่ได้เป็นแค่เรื่องความสวยของโค้ด แต่กระทบผู้ใช้จริงทั้งหมด

**รูปแบบคำตอบของข้อผิดพลาดมีสามแบบปนกัน** — `{ error }`, `{ message }` และ
`{ message, error }` ฝั่งเว็บจึงต้องเขียนโค้ดอ่านแบบนี้กระจายอยู่ทุกหน้า

```js
err.response?.data?.error || err.response?.data?.message || err.message
```

แล้วบางหน้าลืมช่องใดช่องหนึ่ง ผู้ใช้เลยเห็น `Request failed with status code 409`
แทนที่จะเห็นว่า "ชื่อนี้มีอยู่แล้ว"

**ข้อความจาก MySQL หลุดออกไปถึงเบราว์เซอร์** — ทุก `catch` ลงท้ายด้วย
`res.status(500).json({ error: err.message })` ทำให้คำตอบที่ส่งออกไปมีข้อความอย่าง
`Unknown column 'd.brand_i' in 'field list'` ซึ่งบอกชื่อตาราง ชื่อคอลัมน์ และ
โครงสร้างฐานข้อมูลให้คนนอกฟรีๆ

**การตรวจข้อมูลขาเข้าไม่สม่ำเสมอ** — `zod` ถูกติดตั้งไว้แล้วแต่ใช้จริงแค่ไฟล์เดียว
ที่เหลือตรวจด้วยมือทีละบรรทัด ทำให้ตรวจไม่ครบ (ไม่เช็คความยาว) แปลงชนิดไม่ตรง
(ฟอร์มส่ง `"3"` แต่ schema ประกาศเป็น number) และ query string ไม่เคยถูกตรวจเลย

**ไม่มีทางไล่ตามปัญหาที่ผู้ใช้แจ้ง** — ล็อกทั้งหมดเป็น `console.error("Stats Error:", ...)`
ที่ไม่มี id ของคำขอ ไม่มีเวลาที่ใช้ ไม่มีว่าใครเรียก พอผู้ใช้บอกว่า "กดแล้วขึ้น error"
เราหาบรรทัดที่ตรงกับเหตุการณ์นั้นไม่เจอ

## การตัดสินใจ

**ทุกข้อผิดพลาดออกจาก API ในรูปแบบ Problem Details (RFC 9457) รูปแบบเดียว
ผ่าน error handler ตัวเดียวที่ `index.js`**

```json
{
  "type": "about:blank",
  "title": "มีข้อมูลนี้อยู่ในระบบแล้ว",
  "status": 409,
  "code": "conflict",
  "detail": "ค่าที่กรอกซ้ำกับรายการที่มีอยู่ กรุณาตรวจสอบแล้วกรอกใหม่"
}
```

RFC 9457 เป็นมาตรฐานกลางของ HTTP API ไม่ใช่รูปแบบที่เราคิดขึ้นเอง — เครื่องมือและ
ไลบรารีภายนอกอ่านได้ตรงๆ และเราไม่ต้องมานั่งถกกันเองว่าช่องไหนควรชื่ออะไร

ข้อตกลงที่มาพร้อมกัน

| เรื่อง | ข้อตกลง | อยู่ที่ |
|---|---|---|
| ข้อผิดพลาด | ApiError + Problem Details | `src/shared/http-error.js` |
| ตรวจข้อมูลขาเข้า | zod ที่ปากทางทุกเส้นทาง | `src/shared/validate.js` |
| ล็อก | JSON บรรทัดเดียวต่อคำขอ พร้อม request id | `src/shared/logger.js` |
| แคช | `Cache-Control` ตามอายุจริงของข้อมูล | `src/shared/cache.js` |
| transaction | `withTransaction()` ห่อไว้ที่เดียว | `src/shared/db.js` |
| handler ที่เป็น async | ห่อด้วย `asyncHandler` | `src/shared/async-handler.js` |

### สองช่องที่ต้องเข้าใจให้ตรงกัน: `title` กับ `code`

- **`title`** คือข้อความภาษาไทยที่เอาไปโชว์ผู้ใช้ได้ทันที เปลี่ยนได้ตลอด
- **`code`** คือค่าคงที่ภาษาอังกฤษที่โค้ดฝั่งเว็บเอาไปเทียบ **ห้ามเปลี่ยน**

การแยกสองอย่างนี้ทำให้ปรับข้อความให้เข้าใจง่ายขึ้นได้โดยไม่ทำให้ตรรกะฝั่งเว็บพัง

### ข้อความของ MySQL ไม่ออกไปข้างนอก

`fromDatabaseError()` แปลง error ที่รู้จักเป็นข้อความภาษาไทยที่บอกวิธีแก้

| รหัสของ MySQL | กลายเป็น |
|---|---|
| `ER_DUP_ENTRY` | 409 "มีข้อมูลนี้อยู่ในระบบแล้ว" |
| `ER_ROW_IS_REFERENCED*` | 409 "ลบไม่ได้เพราะยังมีข้อมูลอื่นอ้างถึงอยู่" |
| `ER_NO_REFERENCED_ROW*` | 400 "ข้อมูลที่เลือกไม่มีอยู่ในระบบแล้ว" |

ส่วน error ที่ไม่รู้จักถือเป็นบั๊กของเรา — บันทึก stack trace ไว้ในล็อกพร้อม
request id แต่ตอบผู้ใช้เพียง "เกิดข้อผิดพลาดในระบบ กรุณาแจ้งผู้ดูแลพร้อมรหัสอ้างอิง"

## ทางเลือกที่พิจารณาแล้วไม่เลือก

**คิดรูปแบบ error ของตัวเอง** — ทำได้และเร็วกว่าตอนเริ่ม แต่ต้องมานั่งตัดสินใจเอง
ทุกเรื่องที่ RFC ตัดสินไปแล้ว (ช่องไหนบังคับ ใช้ media type อะไร ใส่ข้อผิดพลาดรายช่อง
ยังไง) และไม่มีเครื่องมือไหนอ่านได้โดยไม่ต้องสอน

**ปล่อยรูปแบบเดิมไว้แล้วเขียนตัวช่วยฝั่งเว็บอ่านทั้งสามแบบ** — ซ่อนปัญหาไว้ ไม่ได้แก้
และไม่ได้ช่วยเรื่องข้อความของ MySQL ที่หลุดออกไป ซึ่งเป็นปัญหาด้านความปลอดภัย
ไม่ใช่แค่ความสะดวก

**ใช้ไลบรารีอย่าง `http-errors` หรือ `celebrate`** — ทั้งคู่แก้ปัญหาแค่ครึ่งเดียว
และยังต้องเขียนส่วนที่เหลือเองอยู่ดี โค้ดที่ต้องเขียนทั้งหมดรวมกันไม่ถึงสองร้อยบรรทัด
และเป็นส่วนที่ต้องอ่านออกทันทีเวลาเกิดปัญหาจริง

**ใช้ pino หรือ winston สำหรับล็อก** — ที่โรงพยาบาลนี้ล็อกถูกอ่านด้วยตาจากหน้าจอ
หรือไฟล์ที่ระบบ service เก็บให้ ไม่มี log aggregator ที่ต้องต่อ transport ประโยชน์
ที่เหลือของไลบรารีเหล่านั้นคือความเร็วตอนเขียนล็อกมหาศาล ซึ่งไม่ใช่สถานการณ์ของระบบ
ที่มีผู้ใช้ระดับสิบคน

## ผลที่ตามมา

- ฝั่งเว็บอ่าน error ที่เดียวคือ `src/lib/api-error.js` ทุกหน้าใช้ตัวเดียวกัน
- ข้อผิดพลาดของฟอร์มมี `errors[]` รายช่อง ทำให้วางข้อความไว้ใต้ช่องที่ผิดได้จริง
  แทนที่จะโยนทุกอย่างขึ้น toast ก้อนเดียว
- คำตอบใช้ `Content-Type: application/problem+json` ไม่ใช่ `application/json`
- ล็อกหนึ่งบรรทัดต่อคำขอ มี request id ที่ส่งกลับใน header `x-request-id` ด้วย
  ผู้ใช้แจ้งปัญหาพร้อมรหัสนี้แล้วเราไล่หาเจอทันที
- **ข้อควรระวัง:** เส้นทางใหม่ทุกเส้นต้องห่อด้วย `asyncHandler` และโยน `ApiError`
  แทนการเรียก `res.status().json()` เอง ไม่งั้นจะกลับไปมีรูปแบบที่สี่
- **ข้อควรระวัง:** `TRUST_PROXY_HOPS` ต้องตั้งให้ตรงกับจำนวนชั้น proxy จริงตอน
  deploy ไม่งั้นตัวจำกัดจำนวนครั้งล็อกอินจะนับทุกคนเป็น IP เดียวกัน แล้วคนคนเดียว
  ที่พิมพ์รหัสผิดสิบครั้งจะล็อกทั้งโรงพยาบาลออกจากระบบ
