# 0025 — ชื่อเรียกอื่นของยี่ห้อ อาคาร และฝ่าย

**สถานะ:** Accepted — ผู้ใช้อนุมัติให้เริ่มเมื่อ 2026-09-22 (#130)

## บริบท

ไฟล์จริงสี่ชุด (ทะเบียน OKI/HP, รายงานมิเตอร์ SUTH 86/2567 และ SUTH192/2568, เทมเพลตมิเตอร์เดิม) เรียกข้อมูลหลักตัวเดียวกันต่างกัน พบชื่ออาคาร 29 แบบสำหรับอาคารประมาณ 12 แห่ง เช่น "อาคารศูนย์ความเป็นเลิศทางการแพทย์", "ศูนย์ความเป็นเลิศทางการแพทย์ (EMC)" และ "ศูนย์ความเป็นเลิศ" และชื่อฝ่าย 14 แบบสำหรับ 11 ฝ่าย ซึ่งบางแบบสะกดผิด เช่น "ประสาทเครือข่าย" แทน "ประสานเครือข่าย"

ตัวนำเข้าจับคู่ด้วยชื่อที่ต้องตรงทุกตัวอักษร ผลคือแถวถูกปฏิเสธ หรือสคริปต์สร้างข้อมูลหลักใหม่ตามชื่อในไฟล์ แล้วรายงานรายอาคารแตกเป็นหลายแถวของอาคารเดียวกัน ไฟล์มาจากผู้ให้เช่าทุกเดือน การขอให้แก้ไฟล์ก่อนนำเข้าไม่ยั่งยืน

## การตัดสินใจ

- ตาราง `brand_alias`, `building_alias`, `division_alias` เก็บชื่อที่ไฟล์ใช้ ชี้ไปข้อมูลหลักหนึ่งรายการ ลบข้อมูลหลักแล้วชื่อเรียกอื่นหายตาม
- ชื่อหนึ่งชี้ได้รายการเดียว: ชื่อเรียกอื่นไม่ซ้ำกัน (UNIQUE) ห้ามตรงกับชื่อหลัก และชื่อหลักที่เพิ่มหรือแก้ใหม่ห้ามตรงกับชื่อเรียกอื่น API ตรวจสองข้อหลังด้วยคีย์เดียวกับตัวจับคู่
- การเทียบชื่ออยู่ที่ `apps/api/src/master-data/names.js` ที่เดียว ยุบช่องว่าง ตัดอักขระที่มองไม่เห็น ไม่สนตัวพิมพ์เล็กใหญ่ (ตรงกับ `utf8mb4_unicode_ci`) และถือว่า "ำ" กับ "ํ" + "า" เป็นตัวเดียวกัน **ไม่มีการเดาชื่อใกล้เคียง** ชื่อที่ไม่รู้จักคืนค่าว่างให้คนตัดสิน
- เพิ่มชื่อเรียกอื่นผ่าน API (ผู้ดูแลเท่านั้น) และสคริปต์ `scripts/master-data/load-master-data.cjs` ซึ่งหยุดทั้งหมดก่อนเขียนถ้า plan ขัดกับข้อมูลในระบบ
- ยังไม่ทำกับชั้นและแผนก เพราะชื่อซ้ำกันได้คนละอาคาร/ฝ่าย ชื่อเรียกอื่นต้องผูกตารางแม่ด้วย จะทำเมื่อเจอกรณีจริงตอนปรับตัวนำเข้าทะเบียน

## ทางเลือกที่ไม่เลือก

- **ตารางเดียวแบบ `(entity, alias, target_id)`** — มี foreign key ไม่ได้ ชื่อเรียกอื่นจะชี้ไปรายการที่ถูกลบแล้วได้โดยไม่มีอะไรกัน
- **จับคู่ชื่อใกล้เคียงอัตโนมัติ (fuzzy)** — "รังสีวินิจฉัย" กับ "ศูนย์รังสี" หรือ "พยาธิวิทยา (PYT)" กับ "อาคารพยาธิ" ต้องใช้คนที่รู้จักโรงพยาบาลตัดสิน ระบบที่เดาผิดเงียบๆ ทำให้ค่าใช้จ่ายไปลงผิดอาคาร
- **แก้ชื่อในไฟล์ก่อนนำเข้าทุกเดือน** — งานมือซ้ำทุกเดือนและผิดง่ายที่สุด

## ผลที่ตามมา

- ฐานเดิมต้องรัน `migration_add_master_aliases.sql` ก่อน API รุ่นนี้จะเปิด (ตัวตรวจ schema บอกเอง)
- ขั้นถัดไปคือให้ตัวนำเข้าทะเบียนใช้ `createNameResolver` แทนการเทียบชื่อตรงๆ แล้วรายงานชื่อที่ยังจับคู่ไม่ได้ให้ผู้ดูแลเลือกว่าเป็นรายการใหม่หรือชื่อเรียกอื่น
- ยังไม่มีหน้าเว็บจัดการชื่อเรียกอื่น ผู้ดูแลใช้ API หรือสคริปต์ไปก่อน
- ด่านกันชนเป็นแบบอ่านแล้วเขียน ไม่ได้ล็อกตาราง ผู้ดูแลสองคนที่เพิ่มชื่อหลัก "X" กับชื่อเรียกอื่น "X" ในเสี้ยววินาทีเดียวกันยังผ่านได้ทั้งคู่ (อยู่คนละตาราง UNIQUE จับไม่ได้) รับได้เพราะงานนี้ทำโดยผู้ดูแลไม่กี่คน และตัวจับคู่ให้ชื่อหลักชนะ ถ้าเกิดจริงค่อยเพิ่มคอลัมน์คีย์ที่ UNIQUE ร่วมกัน
- seed ที่ปิด `FOREIGN_KEY_CHECKS` ต้องลบตาราง `*_alias` เอง เพราะ CASCADE ไม่ทำงานตอนปิด
