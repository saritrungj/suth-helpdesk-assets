# 0016 — ฐาน QA แยก และ harness ที่ต่อ MySQL ตรงเฉพาะ bootstrap

**สถานะ:** Accepted

จำกัดขอบเขตข้อห้าม "ทางเข้าที่สองเข้าฐานข้อมูล" ที่ย้ายมาจาก [ADR-0012](0012-remove-mcp-server.md)

## บริบท

งาน #48 เปลี่ยนการแก้ไขและย้ายเครื่องไปอยู่ในแผงข้าง flow จริงคือ `PUT` ข้อมูลเครื่อง
แล้ว `PUT` move ต่อกันสองคำขอ ซึ่งพิสูจน์ด้วย fixture ที่ intercept HTTP ไม่ได้จริง —
สิ่งที่ต้องเห็นคือจำนวนช่วงประวัติหลังย้ายซ้ำวันเดียวกัน ยอดสุทธิที่ไม่เปลี่ยนหลังย้าย
และ 403 ของ staff/viewer ที่มาจาก policy จริงในชั้น API ไม่ใช่จาก mock ที่เราเขียนเอง

ทดสอบเรื่องเหล่านี้บนฐาน `hospital_it_asset` ไม่ได้ เพราะมันคือข้อมูลจริงของโรงพยาบาล
การย้ายเครื่องและแก้รุ่นทิ้งประวัติไว้ถาวร และรายงานค่าใช้จ่ายอ่านจากประวัติเดียวกันนั้น

จึงเตรียมฐาน `hospital_it_asset_qa48` แยกพร้อมข้อมูลจำลอง 25 เครื่อง บัญชีสามระดับ
และ harness `scripts/qa48/` ที่เปิด API 3001 / web 5174 คู่กัน ปัญหาคือ harness นี้
ต่อ MySQL ตรง ซึ่ง `AGENTS.md` ห้ามไว้ตรงตัว — ข้อห้ามนั้นมีเหตุผลที่ยังถูกอยู่ คือ
กฎสิทธิ์ทั้งหมดอยู่ในชั้น API ทางเข้าที่สองแปลว่าต้องเขียนกฎซ้ำแล้วรอวันที่ไม่ตรงกัน

## การตัดสินใจ

**เก็บ harness ไว้ โดยจำกัดการต่อ MySQL ตรงให้เหลือสามอย่างที่ API ทำแทนไม่ได้**

1. ตรวจตัวตนของ runtime ก่อนรันทุกครั้ง — `SELECT DATABASE(), CURRENT_USER()` เพื่อยืนยัน
   ว่ากำลังชี้ฐาน QA ด้วยบัญชี `suth_qa48@localhost` ไม่ใช่ฐานเดิม เป็น metadata ล้วน
2. ตรวจ sentinel ก่อน bootstrap — นับบัญชีจำลองสามรายและยืนยันว่ามีบัญชี runtime อยู่แล้ว
   ถ้าไม่ตรงให้ปฏิเสธ ไม่สร้างฐาน ไม่แก้ schema หรือ grants
3. หมุนรหัสของฐาน QA ตอน `provision` ที่ได้รับอนุมัติแยก — `ALTER USER` และ `UPDATE users
   SET password` เฉพาะสามบัญชีจำลอง ไม่มี endpoint ไหนในระบบทำสองอย่างนี้ให้ได้

**ข้อมูลธุรกิจทุกชิ้นยังต้องผ่าน HTTP API เดิม** — การอ่าน สร้าง แก้ไข ย้าย และการตรวจผล
ทั้งหมดในชุด verify/regression ยิงผ่าน API 3001 หรือผ่านเบราว์เซอร์ กฎสิทธิ์จึงยังอยู่
ที่เดียว และผลที่ได้เป็นหลักฐานของ policy จริง ไม่ใช่ของ SQL ที่ harness เขียนเอง

ขอบเขตอื่นที่ผูกมากับการตัดสินใจนี้:

- บัญชี runtime มีเฉพาะ SELECT/INSERT/UPDATE/DELETE บน schema QA ไม่มีสิทธิ์ข้ามฐาน
- ความลับอยู่ใน `output/qa48/credentials.clixml` ผ่าน Windows DPAPI อยู่ใน gitignore
  ห้ามแนบไปกับรายงานหรือ checkpoint และไม่ใช่ secret manager สำหรับ production
- ข้อห้ามเดิมยังมีผลเต็มกับโค้ดแอปพลิเคชันและเครื่องมือ AI ทุกตัว ADR นี้ไม่ผ่อนให้
  `apps/api`, `apps/web` หรือเครื่องมือใดต่อ MySQL ตรง

## ทางเลือกที่พิจารณาแล้วไม่เลือก

**ทดสอบ live-write บนฐานเดิม** — ไม่ต้องมี harness เลย แต่แลกกับการทิ้งประวัติตำแหน่ง
ปลอมไว้ในข้อมูลจริงที่รายงานค่าใช้จ่ายอ่านอยู่ ราคาที่จ่ายสูงกว่าปัญหาที่แก้มาก

**bootstrap ผ่าน API อย่างเดียว** — ตรงกับกฎที่สุด แต่ทำไม่ได้จริง ระบบไม่มี endpoint
สำหรับสร้างหรือหมุนรหัสบัญชี MySQL และไม่ควรมี เพราะนั่นคือการเปิดช่องจัดการฐานข้อมูล
ผ่านเว็บ ซึ่งอันตรายกว่าสคริปต์ที่รันด้วยมือบนเครื่องเดียว

**เลิกทดสอบ live-write ใช้ fixture อย่างเดียว** — ทำให้ไม่มีอะไรยืนยันว่าสองคำขอของ
flow แก้ไข–ย้ายทำงานถูกกับ policy และประวัติจริง ข้อบกพร่องแบบนั้นจะโผล่ตอนใช้งานจริง
ซึ่งคือเวลาที่แพงที่สุด

## ผลที่ตามมา

- `AGENTS.md` ชี้มาที่ ADR นี้เป็นข้อยกเว้นเดียวของกฎ "ห้ามเปิดทางเข้าที่สอง"
- ถ้าวันหนึ่ง harness เริ่มเขียน SQL ที่แตะข้อมูลธุรกิจ — ทะเบียน ยอดพิมพ์ ประวัติ
  ตำแหน่ง — นั่นคือการละเมิด ADR นี้ ต้องกลับมาทบทวนก่อน ไม่ใช่ขยายเงียบๆ
- ฐาน QA ถูกเก็บไว้ ไม่ reset ข้อมูลจึงสะสมทุกรอบ live-write และรอบหลังต้องอ่านสถานะ
  ปัจจุบันก่อน ไม่ใช่สมมติว่าเริ่มจากศูนย์
- ฐาน QA มีชื่อหน่วยงานยาวและเครื่องที่มีประวัติย้าย ซึ่งเปิดเผยข้อบกพร่องที่ฐานเดิม
  ไม่เคยสร้างสถานะให้เจอ ดู [ผลตรวจ accessibility](../reference/accessibility.md)
