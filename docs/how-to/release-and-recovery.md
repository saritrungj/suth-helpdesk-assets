# ส่งรุ่น ตรวจหลังส่ง และกู้คืน

ใช้คู่มือนี้เมื่อมีสภาพแวดล้อม production และผู้รับผิดชอบจริงแล้ว ก่อนครั้งแรกต้องทำ
[checklist เตรียมขึ้น production](prepare-for-production.md) ให้ครบ โดยเฉพาะ backup,
การซ้อม restore และช่องทางติดต่อเมื่อระบบล่ม การ deploy, migration, secret และ
การเขียนข้อมูลจริงต้องได้รับอนุมัติตาม [CONTRIBUTING.md](../../CONTRIBUTING.md)

## บันทึกก่อนเริ่มแต่ละรอบ

ใน PR หรือบันทึก release ให้ระบุ commit ที่จะส่ง, ผู้ตัดสินใจ, ผู้ปฏิบัติ, ช่วงเวลา,
ผล `npm run verify` และ `npm run verify:db` ที่เกี่ยวข้อง, สิ่งที่ไม่ได้ทดสอบ,
ผลกระทบต่อผู้ใช้, schema/migration, และวิธีกลับสู่รุ่นก่อนหน้า
ถ้ามี migration ให้สำรองฐานและซ้อมกับสำเนาตาม
[คู่มือ migration](run-migrations.md) ก่อน อย่าถือว่าการย้อนโค้ดจะย้อนข้อมูลได้เอง

## ตรวจหลังส่ง

1. ตรวจว่า commit และ config ที่รันตรงกับที่อนุมัติ โดยไม่พิมพ์ค่าความลับลง log
2. ตรวจ `/api/health/live` และ `/api/health` ตาม
   [API reference](../reference/api.md) — ค่า 200 ของตัวแรกอย่างเดียวไม่ยืนยันว่าฐานพร้อม
3. ล็อกอินด้วยบัญชีทดสอบที่ได้รับอนุญาต แล้วอ่านทะเบียน, เดือนยอดพิมพ์,
   Dashboard และรายงานในปีงบเดียวกัน ตรวจว่าตัวเลขและช่วงเดือนสัมพันธ์กันตาม
   [เส้นทางงานสำคัญ](../explanation/workflows.md)
4. ตรวจ log แบบมี request ID เมื่อคำขอผิดพลาด และบันทึกเวลาเริ่ม/จบ ผลตรวจ
   ผู้ตรวจ และปัญหาที่พบใน release record การทดสอบที่เขียนข้อมูลให้ทำบนฐาน QA แยก
   เว้นแต่ได้รับอนุมัติให้ทำกับ production โดยเฉพาะ

ถ้าผลตรวจสำคัญไม่ผ่าน ให้หยุดเปิดใช้งานรุ่นนั้น ประเมินการย้อนโค้ดและการกู้ข้อมูล
แยกกัน แล้วแจ้งผู้รับผิดชอบตามช่องทางที่กำหนดก่อนขึ้นใช้จริง

## เมื่อเกิดเหตุขัดข้อง

1. คนรับเหตุบันทึกเวลาเริ่ม อาการ ผลกระทบต่อผู้ใช้ และ request ID ที่เกี่ยวข้อง
   ระบุผู้ประสานงานหนึ่งคนให้ตัดสินลำดับงานและสื่อสารสถานะ
2. ตรวจ health, log, การเปลี่ยนแปลงล่าสุด และขอบเขตข้อมูลที่ได้รับผลกระทบ
   ลดผลกระทบก่อนหาสาเหตุทั้งหมด การย้อนรุ่นหรือกู้ฐานต้องผ่านผู้มีอำนาจและ
   ใช้ backup ที่ตรวจแล้ว
3. หลังกลับมาทำงาน บันทึกเวลาฟื้นตัว สิ่งที่ตรวจยืนยัน และข้อมูลที่ยังต้องตรวจ
4. ทำบทเรียนหลังเหตุโดยไม่โทษบุคคล เปิด Issue ที่มีเจ้าของและเกณฑ์ปิดชัดเจน
   สำหรับ test, monitoring, ขั้นตอนกู้คืน หรือกฎที่ต้องปรับ แล้วติดตามจนปิดจริง

ก่อนเริ่ม production ให้เติมชื่อผู้รับเหตุ ช่องทางติดต่อ และที่เก็บ release/incident
record ในระบบปฏิบัติการของหน่วยงาน; อย่าใส่ข้อมูลผู้ใช้หรือ secret ลงใน GitHub Issue
แนวทางเลือกการตรวจจากเส้นทางผู้ใช้และการปิด action หลังเหตุอ้างจาก
[Google SRE SLO](https://sre.google/workbook/implementing-slos/) และ
[Google SRE postmortems](https://sre.google/workbook/postmortem-culture/)
