# ขอบเขต API

prefix และความรับผิดชอบ — รายละเอียด endpoint, payload และ response ให้อ่านจาก `apps/api/src/<feature>/routes.js` โดยตรง เพื่อไม่ให้เอกสารกลายเป็นสำเนาของโค้ดที่ล้าสมัย

การยืนยันตัวตนใช้ **cookie แบบ httpOnly** (`suth_session`) ที่ `POST /api/auth/login` ตั้งให้ เบราว์เซอร์แนบไปเองทุก request — เว็บอ่าน token เองไม่ได้ ดู [ADR-0006](../decisions/0006-session-cookie-instead-of-localstorage.md)

สำหรับ script หรือ curl ที่ไม่มีที่เก็บ cookie ยังส่ง `Authorization: Bearer <token>` ได้เหมือนเดิม

| Endpoint | ต้องล็อกอิน | หน้าที่ |
|---|---|---|
| `POST /api/auth/login` | ไม่ | ตรวจรหัสผ่าน ตั้ง cookie แล้วคืนข้อมูลผู้ใช้ (ไม่คืน token) |
| `GET /api/auth/me` | ใช่ | บอกว่าตอนนี้เป็นใคร — เว็บเรียกตอนเปิดหน้าเพราะอ่าน cookie เองไม่ได้ |
| `POST /api/auth/logout` | ไม่ | ลบ cookie ทิ้ง เรียกได้แม้ token หมดอายุแล้ว |

เส้นอื่นทั้งหมดต้องล็อกอิน

| `/api/devices` | ทะเบียนอุปกรณ์ การย้าย และประวัติ | `src/devices/` |

| `/api/print-transactions` | ยอดพิมพ์และสรุปตามปีงบ | `src/print-usage/` |
| `/api/dashboard` | KPI รายงาน และการเปรียบเทียบ | `src/dashboard/` |
| `/api/expense` | ค่าใช้จ่ายตามปีงบ และอุปกรณ์ที่ไม่มีสัญญา | `src/expense/` |
| `/api/users` | จัดการผู้ใช้ (admin เท่านั้น) | `src/users/` |
| `/api/health` | ตรวจว่าระบบพร้อมรับงาน (ไม่ต้องล็อกอิน) | `src/health/` |

## เส้นทางที่ตอบคำถามหลายข้อในคำขอเดียว

สองเส้นนี้ต่างจากเส้นอื่นตรงที่ไม่ได้สะท้อนตารางใดตารางหนึ่ง แต่ประกอบคำตอบให้ตรงกับ
สิ่งที่หน้าจอต้องใช้จริง เพื่อตัดจำนวนคำขอที่เบราว์เซอร์ต้องยิงตอนเปิดหน้า

| Endpoint | ตอบอะไร |
|---|---|
| `GET /api/dashboard/overview` | ยอดรวม + เส้นแนวโน้มทั้งปีงบ + สถานะเครื่อง + อันดับแผนก + **รายการที่ต้องลงมือทำ** |
| `GET /api/print-transactions/coverage` | เดือนไหนของปีงบกรอกครบแล้ว เดือนไหนขาดกี่เครื่อง |

`overview` แทนคำขอห้าเส้นที่หน้าแรกเคยยิงพร้อมกัน และให้สิ่งที่คำนวณฝั่งเบราว์เซอร์
ไม่ได้เลย คือ "รายการที่ต้องลงมือทำ" ซึ่งต้องรู้ทั้งความครบถ้วนของการกรอกและราคาที่
ผูกกับแต่ละเครื่องพร้อมกัน

### สองตัวเลขที่ห้ามสลับกัน

คำตอบของ `overview` มีตัวเลขสองชุดที่ฟังดูเหมือนกันแต่ตอบคนละคำถาม

| ช่อง | นับอะไร | ใช้ตอบคำถามว่า |
|---|---|---|
| `coverage.complete_months` / `coverage.elapsed_months` | **เดือน** ที่กรอกครบทุกเครื่องแล้ว เทียบกับเดือนที่ผ่านไปแล้วในปีงบ | "ข้อมูลครบพอจะเชื่อตัวเลขได้หรือยัง" |
| `totals.reporting_active_devices` / `totals.active_devices` | **เครื่อง** ที่มียอดอย่างน้อยหนึ่งเดือนในช่วงที่เลือก | "มีเครื่องไหนที่ไม่เคยส่งยอดเลยไหม" |

**ป้าย "ความครบถ้วนของข้อมูล" บนหน้าเว็บหมายถึงชุดแรกเสมอ** เคยมีบั๊กที่เอาชุดที่สอง
มาแสดงใต้ป้ายนั้น ทำให้หน้าแรกขึ้นว่า "18/18 กรอกครบแล้ว" พร้อมกับแผงที่อยู่ห่างไป
ไม่ถึงสองนิ้วบอกว่า "ยังกรอกยอดพิมพ์ไม่ครบ 5 เดือน"

`coverage.total_months` เท่ากับ 12 และ `annual_complete_months` นับเดือนที่กรอกครบตลอดปีงบ รวมเดือนปัจจุบันที่กรอกครบแล้ว หน้าเว็บใช้คู่นี้เป็นความครบถ้วนทั้งปี

`complete_months` / `elapsed_months` ยังคงนับเฉพาะเดือนที่จบแล้วเพื่อรักษาสัญญา API เดิม ส่วน `incomplete_months` คือเดือนที่จบแล้วแต่กรอกไม่ครบ และ `not_due_months` คือเดือนที่ยังไม่จบและกรอกไม่ครบ ดังนั้นกรอกครบ 6 เดือนในเดือนกันยายนอาจแสดง 6/12 พร้อมงานค้าง 5 เดือนและยังไม่ถึงกำหนด 1 เดือน

`months` แจกแจง `month`, `filled_devices`, `missing_devices`, `status` (`complete`, `overdue`, `not_due`, `not_applicable`) ทั้ง 12 เดือน หากไม่มีเครื่อง active จะได้ `applicable: false` และแสดงว่าไม่มีเครื่องในขอบเขตนี้ ตรรกะอยู่ที่ `packages/domain/coverage.cjs` และทดสอบที่ `packages/domain/coverage.test.js` กับ `apps/api/test/dashboard-coverage.test.js`

รายงานที่คืนยอดรายเดือน (`monthly-kpi`, `compare`, `summary-by-building`, `expense`, `highlights` และ `overview`) ใช้อาคาร ชั้น ตำแหน่ง ฝ่าย และแผนกจาก `device_location_history` ที่มีผลในเดือนนั้น หากช่วงประวัติซ้อนกันจะเลือกช่วงตาม [ADR-0014](../decisions/0014-resolve-overlapping-location-history.md) เพื่อไม่ให้ยอดหนึ่งรายการถูกบวกซ้ำ

### ข้อจำกัดที่ต้องรู้ก่อนเอา `coverage` ไปใช้ตัดสินใจ

**1. ตัวส่วนคือจำนวนเครื่องที่ `active` อยู่ ณ ตอนที่เรียกดู ไม่ใช่ ณ เดือนนั้น**

ฐานข้อมูลตอนนี้เก็บแค่ `devices.status` ที่เป็นค่าปัจจุบัน **ไม่มีคอลัมน์บอกว่า
เครื่องเข้าระบบหรือถูกปลดระวางเมื่อไหร่** ระบบจึงตอบไม่ได้ว่า "เดือน ธ.ค. มีเครื่อง
ที่ต้องอ่านมิเตอร์กี่เครื่อง" และใช้จำนวนเครื่องปัจจุบันแทนทุกเดือน

ผลที่ตามมาซึ่งเกิดขึ้นจริงได้

| เหตุการณ์ | สิ่งที่ระบบแสดง |
|---|---|
| ซื้อเครื่องใหม่เพิ่มกลางปี | เดือนก่อนหน้าที่เคยครบ กลายเป็น "ไม่ครบ" ย้อนหลัง |
| ปลดระวางเครื่องกลางปี | เดือนก่อนหน้าดู "ครบ" ง่ายกว่าความจริง |

การแก้ให้ถูกต้องต้องเพิ่มคอลัมน์ช่วงเวลาที่เครื่องอยู่ในระบบ (**เปลี่ยน schema —
ต้องขออนุมัติ**) หรือตกลงกันว่าจะใช้ `device_location_history.effective_from`
เป็นตัวแทนวันเริ่มใช้งาน (**เป็นการตั้งกฎธุรกิจใหม่ ต้องมีคนตัดสินใจ**) ทั้งสองทาง
ยังไม่ได้ทำ และ **ห้ามเปลี่ยนเงียบๆ ในโค้ด**

**2. ตัวเศษกับตัวส่วนต้องมาจากขอบเขตเดียวกันเสมอ**

เมื่อกรองด้วย `building_name` ทั้งจำนวนเครื่องที่กรอกแล้วและจำนวนเครื่องที่ใช้งาน
อยู่ ต้องถูกกรองด้วยอาคารเดียวกัน เคยมีบั๊กที่คิวรี่ตัวเศษไม่ได้กรอง ทำให้อาคารที่
มีเครื่อง 3 เครื่องถูกเทียบกับยอดกรอกรวมทุกอาคาร (18) แล้วรายงานว่าครบทุกเดือน
ทั้งที่อาคารนั้นยังไม่ได้กรอกเลย — มีเทสกันไว้แล้วที่
`test/dashboard-coverage-sql.test.js` (ตรวจระดับ SQL จึงไม่ขึ้นกับข้อมูลในฐาน) และ
`test/dashboard-coverage-scope.test.js` (เทียบผลจริงกับข้อมูลดิบ)

## การกรองในทะเบียนเครื่อง

`GET /api/devices` รับพารามิเตอร์ต่อไปนี้ ทุกตัวไม่บังคับ — **ไม่ส่งอะไรมาเลยจะคืน
ทุกเครื่องเรียงตามหมายเลข เหมือนเดิมทุกประการ**

| พารามิเตอร์ | ความหมาย |
|---|---|
| `q` | ค้นในหมายเลขเครื่อง รุ่น ยี่ห้อ และที่ตั้งพร้อมกัน |
| `building_id` `floor_id` `division_id` `department_id` `brand_id` `contract_id` | กรองตามรหัส |
| `status` | `active` \| `repair` \| `retired` |
| `unassigned` | `true` = เฉพาะเครื่องที่ยังไม่ผูกสัญญา |
| `fiscal_year_id` | แนบสรุปยอดพิมพ์ของปีงบนั้นมากับแต่ละเครื่อง (`usage`) |
| `sort` `order` | คอลัมน์ที่เรียงและทิศทาง |
| `page` `per_page` | แบ่งหน้า (สูงสุด 200) — ส่ง `per_page` มาเมื่อไหร่จึงจะแบ่ง และจะมี `X-Total-Count` ในคำตอบ |

## Health check

| Endpoint | ตรวจอะไร | ใช้ตอนไหน |
|---|---|---|
| `GET /api/health/live` | โปรเซสยังตอบอยู่ไหม (ไม่แตะฐานข้อมูล) | ตัดสินว่าควรรีสตาร์ตโปรเซสไหม |
| `GET /api/health` | พร้อมรับงานจริงไหม — ping ฐานข้อมูลด้วย | ตัดสินว่าควรส่งผู้ใช้มาที่เครื่องนี้ไหม |

ต่อฐานข้อมูลไม่ได้ `GET /api/health` จะตอบ **503** ไม่ใช่ 500 — 503 แปลว่า "ยังไม่พร้อม
ลองใหม่ทีหลัง" ซึ่งเป็นสถานการณ์จริงตอนฐานข้อมูลกำลังรีสตาร์ต ส่วน 500 แปลว่าโค้ดพัง

`GET /` ไม่ใช่ health check — คืนแค่ชื่อของ API และลิงก์ไปยัง health check ตัวจริง

## รูปแบบของข้อผิดพลาด

ทุกข้อผิดพลาดออกมาในรูปแบบ Problem Details ([RFC 9457](https://datatracker.ietf.org/doc/html/rfc9457))
พร้อม `Content-Type: application/problem+json` — ดู [ADR-0010](../decisions/0010-problem-details-and-api-conventions.md)

```json
{
  "type": "about:blank",
  "title": "มีข้อมูลนี้อยู่ในระบบแล้ว",
  "status": 409,
  "code": "conflict",
  "detail": "ค่าที่กรอกซ้ำกับรายการที่มีอยู่ กรุณาตรวจสอบแล้วกรอกใหม่"
}
```

- **`title`** ข้อความภาษาไทยที่เอาไปโชว์ผู้ใช้ได้ทันที — เปลี่ยนได้
- **`code`** ค่าคงที่ที่โค้ดเอาไปเทียบ — **ห้ามเปลี่ยน**
- **`errors[]`** มีเฉพาะข้อผิดพลาดของฟอร์ม (400) เป็นรายการ `{ field, message }` รายช่อง

ฝั่งเว็บอ่านคำตอบเหล่านี้ที่ `apps/web/src/lib/api-error.js` ที่เดียว

## รหัสตอบกลับที่ใช้

| รหัส | ความหมาย |
|---|---|
| `400` | ข้อมูลที่ส่งมาไม่ถูกต้อง เช่น รูปแบบเดือนผิด หรือกรอกไม่ครบ |
| `401` | ไม่มี token, token หมดอายุ หรือรหัสผ่านผิด |
| `403` | ล็อกอินแล้วแต่สิทธิ์ไม่พอ |
| `404` | ไม่พบข้อมูลที่อ้างถึง |
| `409` | ชนกับข้อมูลที่มีอยู่ (ชื่อซ้ำ) หรือลบไม่ได้เพราะยังมีข้อมูลอื่นอ้างถึง |
| `429` | ยิงคำขอถี่เกินไป |
| `500` | ข้อผิดพลาดฝั่งเซิร์ฟเวอร์ — คำตอบมี `request_id` ให้แจ้งผู้ดูแลไปไล่ล็อกได้ |
| `503` | ต่อฐานข้อมูลไม่ได้ (เฉพาะ health check) |

การล็อกอินจำกัดไว้ 10 ครั้งต่อ 15 นาทีต่อ IP โดยนับเฉพาะครั้งที่ล้มเหลว
ส่วนคำขอทั่วไปจำกัดที่ 600 ครั้งต่อนาทีต่อ IP (ปรับด้วย `RATE_LIMIT_PER_MINUTE`)

> **ตอน deploy หลัง reverse proxy ต้องตั้ง `TRUST_PROXY_HOPS`** ให้ตรงกับจำนวนชั้น
> proxy จริง ไม่งั้นทุกคำขอจะถูกมองว่ามาจาก IP เดียวกันหมด แล้วคนคนเดียวที่พิมพ์
> รหัสผิดสิบครั้งจะล็อกทุกคนออกจากระบบ

## แคช

| ชนิดข้อมูล | `Cache-Control` |
|---|---|
| ข้อมูลอ้างอิง (อาคาร ชั้น ฝ่าย แผนก ยี่ห้อ สัญญา ปีงบ) | `private, max-age=60, stale-while-revalidate=600, must-revalidate` |
| ข้อมูลปฏิบัติการ (ทะเบียน ยอดพิมพ์ รายงาน) | `private, max-age=0, must-revalidate` |
| บัญชีผู้ใช้ และทุกคำตอบหลังการเขียนข้อมูล | `no-store` |

Express สร้าง ETag ให้อยู่แล้ว คำขอที่สองเป็นต้นไปจึงได้ `304` ตัวเปล่าแทน JSON เต็มก้อน
