# ระบบกับ WCAG 2.2 ระดับ AA

เอกสารนี้บอก **ขอบเขตของเทส ผลการตรวจที่บันทึกไว้ และสิ่งที่ยังไม่ได้ตรวจ**
ชื่อข้อ WCAG บนเทสระบุเรื่องที่เทสช่วยตรวจ ไม่ใช่การรับรองว่าผ่านข้อนั้นครบทุกเงื่อนไข

> ผ่านการวัด ≠ ผ่านการใช้งานจริง หัวข้อ "ยังไม่ได้ตรวจ" คือสิ่งที่เครื่องตรวจแทน
> คนไม่ได้ **ห้ามอ่านข้ามไป** และห้ามสรุปว่าระบบ "เข้าถึงได้แล้ว" จากตารางผลอย่างเดียว

## ทำไมเขียนเอง ไม่ใช้เครื่องมือสำเร็จรูป

รอบแรกใช้เครื่องมือที่มีอยู่โดยไม่เพิ่ม dependency ตัวตรวจที่เขียนเองมีขอบเขตจำกัด
และต้องมี regression tests ของตัวมันเอง ไม่ถือว่าครอบคลุมเทียบเท่าเครื่องมือตรวจมาตรฐาน
หรือการใช้งานด้วย assistive technology จริง — นี่คือเหตุผลที่ต่อมาเพิ่ม axe-core
เป็นอีกชั้นแทนที่จะพึ่งตัววัดที่เขียนเองอย่างเดียว (ดูหัวข้อถัดไป)

## axe-core กับตัววัดที่เขียนเอง แบ่งงานกันอย่างไร

`apps/web/e2e/axe-fixture.spec.js` เพิ่ม [`@axe-core/playwright`](https://github.com/dequelabs/axe-core-npm)
เป็นชั้นพื้นแยกจากตัววัดข้างบน **ไม่ใช่ตัวแทน**:

| | axe-core | ตัววัดที่เขียนเอง (contrast-helper.js ฯลฯ) |
| --- | --- | --- |
| จับอะไร | rule ทั่วไปที่เครื่องตรวจได้ — ARIA ผิด, ป้ายกำกับหาย, role/name ที่ขาด, ปุ่มไม่มีชื่อ ฯลฯ | contrast จาก CSS ที่ compose แล้วจริง ผ่าน canvas ของเบราว์เซอร์ รวม `oklch(...alpha)` และการซ้อนหลายชั้น (ดูหัวข้อ "วิธีวัด contrast" ด้านบน) |
| ทำไมต้องแยก | เขียนเองไม่คุ้ม มีคนดูแล rule set ให้แล้วและอัปเดตตามมาตรฐานเรื่อยๆ | axe ยังจับ contrast ของสีที่ผ่านการ compose/opacity/oklch ได้ไม่แม่นเท่า ตัววัดของเราออกแบบมาเพื่อเคสนี้โดยเฉพาะ |
| ครอบคลุม | ราว 30–50% ของ WCAG (ดูหมายเหตุใน [#64](https://github.com/saritrungj/suth-helpdesk-assets/issues/64)) | เฉพาะ contrast/reflow/target-size ที่ระบุไว้ในตารางด้านบน ไม่ใช่ทั้งหมด |

**สถานะปัจจุบัน (เฟส 1):** รันเฉพาะสถานะที่ fixture คุมอยู่แล้ว — ทะเบียน, แผงแก้ไข,
แผงย้ายเครื่อง — ยังไม่ครบ `PAGES` ของ `wcag.spec.js` เพราะหน้าที่เหลือต้องล็อกอิน
จริงผ่าน API/ฐานข้อมูล ซึ่งชั้น CI นั้นยังไม่มี (#63) เมื่อ #63 เสร็จ เฟส 2 จะขยาย
ไปรันบน `PAGES` ทั้งชุดโดยใช้กลไก baseline เดียวกัน ไม่ต้องออกแบบใหม่

**baseline:** violation ที่มีอยู่ ณ วันเริ่มถูกบันทึกไว้ใน `apps/web/e2e/axe-baseline.json`
CI แดงเฉพาะตัวใหม่ที่ยังไม่เคยอยู่ในนั้น เพื่อให้ไล่เก็บหนี้เดิมทีละตัวได้โดยไม่ต้อง
บล็อกทุก PR จนกว่าจะแก้หมด ตอนเริ่มเจอ `color-contrast` หนึ่งจุดบนทะเบียน/แผงแก้ไข/
แผงย้าย (`.opacity-80`, 4.15:1 จากที่ต้องการ 4.5:1) ซึ่งเป็นหนี้เดิมที่ยังไม่เคยถูก
ตัววัด contrast ของเราวัด เพราะอยู่นอกขอบเขตปัจจุบันของ `contrast-helper.js`

### วิธีวัด contrast

ค่า contrast ที่คำนวณล่วงหน้าจาก token ใช้ได้เฉพาะกรณีที่ตัวหนังสือทึบวางบนพื้นทึบ
ในของจริงมีสองอย่างที่ทำให้ค่านั้นไม่ตรง: ตัวหนังสือบางตัวโปร่งแสง และพื้นบางที่
เกิดจากการซ้อนหลายชั้น (เช่น badge บนการ์ดบนพื้นหน้า)

เทสจึงไม่อ่านค่าจาก token แต่

1. ให้ canvas ของเบราว์เซอร์แปลงสี CSS รวม `oklch(... / alpha)` เป็น RGBA
2. ประกอบ foreground/background ผ่านแต่ละบรรพบุรุษ โดยใช้ opacity กับกลุ่มที่ประกอบเสร็จแล้ว
3. คำนวณ contrast จากสองสีที่ได้ และเปรียบเทียบค่าที่ยังไม่ปัดเศษ

ทดสอบตัววัดด้วยค่าอิสระ: ดำ opacity 0.2 บนขาวต้องได้ประมาณ 1.61:1 ไม่ใช่ 21:1
ตรวจข้อความใน input/textarea และ placeholder แยกจาก text node; ไม่บันทึกค่าที่ผู้ใช้กรอกลงรายงาน
ข้อความใน control ที่ disabled รวมลูกของมันได้รับการยกเว้น ไม่ใช่ข้อผิดพลาด contrast

ให้เบราว์เซอร์เป็นคนแปลง oklch เป็น sRGB แทนที่จะเขียนสูตรเอง เพราะสิ่งที่ต้องวัด
คือสิ่งที่ผู้ใช้เห็นจริง ไม่ใช่สิ่งที่สูตรบอกว่าควรจะเป็น

ถ้าเจอ gradient/image/filter/blend ในสายบรรพบุรุษ ตัววัดรายงาน `unsupported`
ไว้ใน attachment `contrast-report` พร้อม annotation `unmeasured` ไม่เพิ่มจำนวน measured
การผ่านของเทสแปลว่าเฉพาะตัวอย่างที่วัดได้ไม่มี failure ไม่ใช่ว่าส่วน unsupported ผ่านด้วย
ตัววัดไม่จำลอง pseudo-element ซ้อนพื้น, sibling overlays, text-shadow หรือ canvas text
จึงยังต้องตรวจส่วนเหล่านี้แยก หน้าล็อกอินปัจจุบันใช้พื้นทึบและตรวจ contrast ทั้งหน้า รวมส่วนช่วยเหลือที่กางออก

### หมายเหตุเรื่องเทส 1.4.10

เทส reflow **ย่อจอหลังจากโหลดหน้าเสร็จแล้ว** ไม่ใช่เปิดหน้าที่ 320px ตั้งแต่แรก
ตั้งใจให้เป็นแบบนั้น เพราะบั๊กของกราฟ (ดูตารางด้านล่าง) โผล่เฉพาะตอนย่อ —
เปิดที่ 320px ตั้งแต่ต้นไม่เจอ และนั่นคือเหตุผลที่มันรอดสายตามาตลอด
คนที่ซูม 400% เดินเส้นทางเดียวกับที่เทสนี้เดิน

### กฎที่ตามมา

- `--ink-faint` ใช้กับไอคอนประดับเท่านั้น ข้อความรวม placeholder ใช้ `--ink-mute`
  ขึ้นไปและต้องวัดกับพื้นจริง Placeholder ไม่ได้รับข้อยกเว้นจาก WCAG 1.4.3
  กฎเดิมที่อนุญาต placeholder 3.3:1 ถูกแก้แล้ว พร้อม regression ของ CSS จริงทั้งสองธีม
- `truncate` ใช้กับ "ชื่อ" ที่เดาส่วนที่หายได้จากบริบท ไม่ใช้กับประโยคอธิบาย
- ลิงก์ที่อยู่เดี่ยวๆ ในช่องตารางไม่เข้าข้อยกเว้น "อยู่ในประโยค" ของข้อ 2.5.8
  ต้องมีพื้นที่กดอย่างน้อย 24×24

## หน้าล็อกอิน

### Layout ปัจจุบัน (9 กันยายน 2026)

บนจอ desktop แบ่งเป็นพื้นที่แบรนด์ 55% กับพื้นที่ฟอร์ม 45% ฝั่งแบรนด์ใช้ `/brand/suth-horizontal.webp` เต็มภาพบนพื้นขาวคงที่ทั้งสองธีม และฝั่งฟอร์มใช้พื้นทึบตามธีม AuroraCanvas variant `hero` ยังคงเป็นภาพประดับ `aria-hidden` ที่ไม่รับ pointer events และไม่เคลื่อนไหว การกางส่วนช่วยเหลือ ขั้นตอนยืนยันตัวตน และ handler ของ error/session ไม่เปลี่ยน

ช่องกรอกและปุ่มหลักสูงอย่างน้อย 48px ไม่เรียกคีย์บอร์ดบนมือถือทันทีที่เปิดหน้า และภาพไม่ยืดถูกล็อกด้วยเทสอัตราส่วน เทสยังตรวจ contrast, keyboard, pending/error, viewport 320/390/768/1440px และบันทึกภาพไว้ใน `apps/web/e2e/screens/`

แนวทางนี้เป็นการประยุกต์จาก [USWDS Sign-in](https://designsystem.digital.gov/templates/authentication-pages/sign-in/), [GOV.UK Password input](https://design-system.service.gov.uk/components/password-input/) และ [W3C Accessible Authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html) ไม่ใช่การรับรองว่าผ่าน WCAG ทั้งระบบ

ชุด `login.spec.js` และ `login-wcag.spec.js` ผ่านรวม 30 เคสหลังเปลี่ยน layout ครอบคลุมสองธีม การกางส่วนช่วยเหลือ contrast การใช้คีย์บอร์ด สถานะกำลังส่ง/ผิดพลาด และ viewport 320, 390, 768, 1440px โดยตรวจว่าปุ่มหลักอยู่ในจอเริ่มต้น ยังไม่ได้ทดสอบกับ NVDA, Windows forced-colors หรือ Voice Control จริง

หน้านี้มีเทสของตัวเองเพิ่มอีกชุด เพราะเป็นหน้าเดียวที่คนนอกองค์กรเปิดเจอได้
และเป็นด่านเดียวที่ถ้าใช้ไม่ได้ก็คือใช้ทั้งระบบไม่ได้ ไม่มีทางอ้อม

### 3.3.8 ผ่านด้วยเหตุผลอะไร

ข้อนี้ระบุว่า "cognitive function test" — ซึ่งรวมถึง **การจำรหัสผ่าน** — ห้ามเป็น
สิ่งที่บังคับในขั้นตอนใดของการยืนยันตัวตน เว้นแต่มีข้อยกเว้นสี่ข้อรองรับ

ระบบนี้ยังใช้รหัสผ่าน จึงพึ่งข้อยกเว้นข้อที่สอง คือ **Mechanism** — มีกลไกช่วย
ผู้ใช้ทำสิ่งนั้น ซึ่งในที่นี้คือปล่อยให้โปรแกรมจัดการรหัสผ่านกรอกแทน W3C ระบุ
ไว้ตรงๆ ว่าการใช้ช่องชื่อผู้ใช้กับรหัสผ่านนับว่าผ่านได้ "if it enables the user
agent (browsers and third-party password managers) to fill in the fields
automatically"

สิ่งที่ต้องรักษาไว้เพื่อให้ข้อยกเว้นนี้ยังใช้ได้ — เทสล็อกไว้ทุกข้อ

- `autocomplete="username"` และ `autocomplete="current-password"`
- `name` และ `id` ที่ **คงที่** ข้ามการโหลดทุกครั้ง
  (`login-username` / `current-password` ไม่ใช่ `f-v-0` ที่ระบบสร้างให้ตอนรัน)
- ช่องรหัสผ่านเป็นช่องเดียว ไม่แตกเป็นหลายกล่อง
- ไม่ `readonly` และไม่จำกัดความยาวสั้นๆ
- **ไม่บล็อกการวาง** — ข้อกำหนดระบุเรื่องนี้ไว้ตรงตัว

ปุ่มดูรหัสผ่านเป็นของเสริมที่ W3C แนะนำในคำอธิบายข้อนี้ ว่าช่วยคนที่พิมพ์ผิดง่าย

### สิ่งที่เทสหน้าล็อกอินจับได้ตอนเขียนครั้งแรก

ฟอร์มใช้งานได้ปกติทุกอย่าง build ผ่าน ไม่มี error แต่ตกห้าข้อ: ไม่มี `name`,
`id` เป็นเลขรันไทม์ (`f-v-0`), ไม่มี `required`, ปุ่มดูรหัสผ่านมีพื้นที่กดแค่
28×28 และคำอธิบายของปุ่มไม่ได้บอกว่ากดแล้วรหัสผ่านจะโผล่บนหน้าจอ

ต่อมายังพบว่าปุ่มดูรหัสผ่านลอยอยู่ **นอก** ช่องรหัสผ่าน และช่องรหัสผ่านสั้นกว่า
ช่องชื่อผู้ใช้ 48px เพราะ `class="pr-12"` ไปเกาะกล่องหุ้มแทนที่จะเป็น `<input>`
เรื่องนี้เห็นได้จากภาพหน้าจอเท่านั้น เทสตอนนั้นจับไม่ได้ — ตอนนี้จับได้แล้ว
