# Design system ของหน้าเว็บ

เอกสารนี้อธิบายว่า "หน้าตาของระบบ" ถูกประกอบขึ้นจากอะไร และต้องแตะตรงไหนเมื่อจะเปลี่ยนอะไรสักอย่าง เหตุผลที่ตัดสินใจทำแบบนี้อยู่ใน [ADR-0008](../decisions/0008-design-system-tokens-and-ui-kit.md)

## หลักการเดียวที่ต้องจำ

> หน้าจอไม่ตัดสินใจเรื่องหน้าตาเอง — มันประกอบชิ้นส่วนที่ตัดสินใจไว้แล้ว

ถ้าเขียนหน้าใหม่แล้วต้องเลือกสี ขนาดตัวอักษร หรือระยะขอบเอง แปลว่ากำลังทำผิดที่ ให้กลับไปหยิบ token หรือ component ที่มีอยู่ ถ้าไม่มีจริงๆ ให้เพิ่มเข้าไปในชั้นกลางแล้วค่อยใช้

## สามชั้น

```
src/design/   token       สี ตัวอักษร ระยะ เงา จังหวะการเคลื่อนไหว
src/ui/       component   ปุ่ม การ์ด ตาราง ฟอร์ม หน้าต่างซ้อน — ไม่รู้จักเรื่องธุรกิจ
src/app/      เปลือกแอป   แถบเมนู แถบบน ช่องค้นหาคำสั่ง
```

หน้าจอ (`src/views/`) และ component เชิงธุรกิจ (`src/components/`) เรียกใช้ทั้งสามชั้น แต่ชั้นล่างไม่รู้จักชั้นบน — `src/ui/` ห้ามมีคำว่าเครื่องพิมพ์ ปีงบ หรือแผนกอยู่ในไฟล์เด็ดขาด

## App shell contract

ค่า layout กลางอยู่ที่ `design/tokens.css`: sidebar 232px, rail 64px, topbar 56px, content padding 24px, content max 1600px หน้าจอห้ามใส่ตัวเลขชุดนี้ซ้ำเอง

เมนูแบ่งเป็น ภาพรวม → งานประจำ → รายงาน → ตั้งค่าระบบ โดย `app/navigation.js` เป็นเจ้าของชื่อ route, role visibility, breadcrumb และ command search งานประจำเปิดเริ่มต้น และหมวด active เปิดเองเมื่อเข้าผ่าน direct link ตอนเป็น rail ทุกรายการมี accessible name และ tooltip ที่เปิดทั้ง hover/focus

## สี

สีถูกกำหนดเป็นสามระดับใน `src/design/tokens.css` และ **ห้ามข้ามระดับ**

| ระดับ | ตัวอย่าง | ใครใช้ได้ |
|---|---|---|
| Primitive | `--teal-700`, `--n-200` | ชั้น semantic เท่านั้น |
| Semantic | `--surface`, `--ink-mute`, `--danger` | component และหน้าจอ |
| Utility | `bg-surface`, `text-ink-mute` | หน้าจอ (Tailwind สร้างให้จาก semantic) |

ชื่อ semantic บอก **หน้าที่** ไม่ใช่สี เพราะสีเดียวกันเปลี่ยนความหมายตามโหมด `--surface` คือ "พื้นการ์ด" เสมอ ไม่ว่าจะโหมดสว่างหรือมืด component จึงไม่ต้องรู้ว่าตอนนี้โหมดอะไร

ชุดที่ใช้บ่อย

- พื้นผิว ไล่จากล่างขึ้นบน: `canvas` (พื้นหน้าจอ) → `surface` (การ์ด) → `surface-2` (หัวตาราง, ช่องกรอก) → `surface-3` (hover) → `surface-float` (เมนู, หน้าต่างซ้อน)
- ตัวหนังสือ ไล่จากเข้มไปจาง: `ink` (หัวข้อ, ตัวเลขสำคัญ) → `ink-soft` (เนื้อความ) → `ink-mute` (คำอธิบาย) → `ink-faint` (**placeholder เท่านั้น** — ไม่ผ่าน contrast สำหรับข้อความจริง)
- เส้น: `line-soft` (เส้นคั่นในเนื้อหา) → `line` (ขอบกล่อง) → `line-strong` (ขอบกล่องตอน hover)
- เส้นของช่องกรอกโดยเฉพาะ: `field-line` → `field-line-strong` (ตอน hover) — **แยกจาก `line` โดยตั้งใจ** เส้นคั่นในตารางเป็นแค่ตัวช่วยจัดกลุ่ม จะจางแค่ไหนก็ได้ แต่ขอบของช่องกรอกคือสิ่งเดียวที่บอกว่า "ตรงนี้พิมพ์ได้" ซึ่ง WCAG 1.4.11 บังคับให้ต่างจากพื้นอย่างน้อย 3:1 การใช้ `line` ตรงนี้เคยทำให้ช่องกรอกทั้งระบบวัดได้ 1.99:1
- ความหมาย: `brand` / `accent` / `ok` / `warn` / `danger` / `info` แต่ละตัวมีชุดย่อย `-soft` (พื้นอ่อน) `-line` (ขอบ) `-ink` (ตัวหนังสือบนพื้นอ่อน) และ `-on` (ตัวหนังสือบนพื้นทึบ)

### ทำไมต้อง OKLCH

ค่า `L` ใน OKLCH คือความสว่างที่ **สายตามนุษย์รับรู้จริง** ไม่ใช่ค่าทางคณิตศาสตร์แบบ HSL ผลคือสีที่มี L เท่ากันจะดูสว่างเท่ากันจริงไม่ว่าจะเป็นสีอะไร ทำให้ออกแบบสเกลที่ห่างเท่ากันได้ และคำนวณ contrast ล่วงหน้าได้ก่อนเห็นของจริง

ทุกคู่สีในระบบผ่าน WCAG AA (4.5:1 สำหรับข้อความปกติ) แล้วโดยการคำนวณ ตัวเลขที่คำนวณไว้เขียนกำกับอยู่ในคอมเมนต์ของ `tokens.css` — **ถ้าจะเปลี่ยนค่า L ของ token ใดต้องคำนวณ contrast ใหม่ด้วย**

การคำนวณล่วงหน้าใช้ได้กับพื้นทึบเท่านั้น พื้นที่มีชั้นแสงซ้อน (หน้าล็อกอิน) ต้องวัดจากหน้าที่รันจริง เพราะสีพื้นที่แท้จริงเกิดจากการซ้อนของหลายชั้นซึ่งอ่านจาก token ตัวเดียวไม่ได้ — วิธีวัดและตัวเลขที่วัดได้อยู่ใน [ระบบกับ WCAG 2.2](../reference/accessibility.md) และถูกล็อกไว้ด้วย `apps/web/e2e/wcag.spec.js` กับ `login-wcag.spec.js`

### สีแบรนด์

มาจากโลโก้โรงพยาบาลจริง

- **teal** `oklch(0.488 0.050 207)` จากตัว "TH" — เป็นสีหลักของทุกสิ่งที่กดได้
- **ส้ม** `oklch(0.662 0.193 38)` จากตัว "SU" — เป็นสีเน้น ใช้เท่าที่จำเป็น ไม่ใช้เป็นสีปุ่มทั่วไปเพื่อไม่ให้สับสนกับสีแดงของปุ่มลบ

## ตัวอักษร

**Anuphan** เป็นฟอนต์หลักทั้งไทยและละติน เป็นฟอนต์ไม่มีหัวที่ออกแบบมาสำหรับ UI โดยเฉพาะ ตัวเลขคมและอ่านง่ายที่ขนาดเล็ก ซึ่งสำคัญกับระบบที่เต็มไปด้วยยอดพิมพ์และจำนวนเงิน ส่วน **IBM Plex Mono** ใช้เฉพาะรหัสทรัพย์สินและ serial ที่ต้องอ่านทีละตัวอักษร

ขนาดตัวอักษรเล็กกว่าค่าเริ่มต้นของ Tailwind หนึ่งขั้น (`text-base` = 14px ไม่ใช่ 16px) เพราะเป็นเครื่องมือทำงานที่คนเปิดดูข้อมูลหนาแน่นทั้งวัน แต่ `line-height` ถูกเพิ่มขึ้นแทน เพราะสระและวรรณยุกต์ไทยซ้อนกันสองชั้นบน-ล่าง ต้องการที่ว่างแนวตั้งมากกว่าภาษาละติน

ตัวเลขในตารางและบนแกนกราฟใช้ `tabular-nums` (ผ่านคลาส `numeral` หรือใน `<table>` โดยอัตโนมัติ) เพื่อให้ทุกหลักกว้างเท่ากัน คอลัมน์จึงตรงกันจริงและเลขไม่ขยับซ้าย-ขวาตอนค่าเปลี่ยน — แต่ **ห้ามใช้กับตัวเลขใหญ่เดี่ยวๆ** ดูเหตุผลในหัวข้อกราฟด้านล่าง

## กราฟและการนำเสนอข้อมูล

กราฟทุกอันในระบบผ่าน `UiChart` ตัวเดียว เพื่อให้กฎด้านล่างนี้ถูกบังคับที่จุดเดียว
แทนที่จะหวังว่าคนเขียนหน้าใหม่จะจำได้ครบ

### ชุดสีของกราฟ — คำนวณมา ไม่ได้เลือกด้วยตา

สีของเส้นและแท่ง (`--chart-1` ถึง `--chart-8`) **ไม่ได้มาจากการเลือกให้ดูสวย**
แต่มาจากการไล่ลำดับที่เป็นไปได้ทั้งหมดของแปดเฉดสี แล้วให้ตัวตรวจตัดสิน โดยเลือก
ลำดับที่ "คู่สีที่แยกกันยากที่สุด" ห่างกันมากที่สุด

ชุดก่อนหน้านี้เรียง hue ไล่กันสวยงามแต่เลือกด้วยตา และ **ไม่ผ่าน** — สีแดงกับ
เขียวที่อยู่ติดกันเหลือระยะห่างเพียง ΔE 4.1 ภายใต้ deuteranopia แปลว่าคนตาบอดสี
เขียว-แดง ซึ่งพบราว 8% ในผู้ชาย เห็นเป็นเส้นสีเดียวกัน ชุดปัจจุบันอยู่ที่ ΔE 16.2

กฎที่ตามมาจากเรื่องนี้

- **ลำดับสลอตคือกลไกความปลอดภัย ห้ามสลับ** ชุดข้อมูลแรกได้สลอต 1 เสมอ
- **ห้ามวนซ้ำเมื่อเกิน 8 ชุด** ชุดที่ 9 ไม่ใช่การสร้างสีใหม่ ให้ยุบเป็น "อื่นๆ"
  แยกเป็นกราฟย่อยหลายใบ หรือลดจำนวนชุดข้อมูลลง
- **สีผูกกับตัวตน ไม่ผูกกับอันดับ** กรองรายการหนึ่งออกแล้วรายการที่เหลือต้องคงสีเดิม
- **สีแดงสงวนไว้ให้สถานะเท่านั้น** ไม่อยู่ในชุดสีของกราฟ เพื่อไม่ให้เส้นกราฟเส้นหนึ่ง
  ดูเหมือนคำเตือน
- ถ้าจะแก้ค่าสีเหล่านี้ **ต้องรันตัวตรวจใหม่ทั้งสองโหมด** อย่าแก้ด้วยสายตา

### กฎอื่นที่ `UiChart` บังคับไว้

- **มุมมองตารางคู่กับกราฟทุกอัน** สลับได้จากหัวการ์ด เป็นข้อบังคับไม่ใช่ของแถม
  เพราะสีบางสลอตมี contrast ต่ำกว่า 3:1 เทียบกับพื้น จึงต้องมีช่องทางอ่านค่าที่
  ไม่พึ่งสีควบคู่เสมอ และคนที่ใช้โปรแกรมอ่านหน้าจอก็อ่านตารางได้จริง
- **คำอธิบายสีมีเมื่อมีตั้งแต่ 2 ชุดขึ้นไป** ชุดเดียวไม่ต้องมี หัวการ์ดบอกอยู่แล้ว
- **ห้ามแกน y สองแกนบนกราฟเดียว** สองหน่วยที่สเกลต่างกันให้แยกเป็นสองกราฟ
  การเอามาซ้อนกันสร้างความสัมพันธ์ที่ไม่มีอยู่จริงในข้อมูล
- **แท่งเริ่มที่ศูนย์เสมอ เส้นไม่ต้อง** ความยาวของแท่งคือค่า การตัดแกนจึงโกหกขนาด
  ส่วนกราฟเส้นอ่านจากความชัน การบังคับเริ่มที่ศูนย์ทำให้เส้นถูกอัดจนมองไม่เห็น
- **ตัวกรองอยู่แถวเดียวเหนือทุกอย่างที่มันคุม** ห้ามมีตัวกรองซ่อนในการ์ดใดการ์ดหนึ่ง
  ไม่งั้นตัวเลขบนหน้าเดียวกันจะอ้างอิงคนละช่วงโดยที่ผู้ใช้ไม่รู้ตัว
- **ตอนโหลดใหม่ กราฟเดิมค้างไว้แบบจาง** ไม่กระพริบเป็นโครงร่าง เลย์เอาต์จึงไม่กระโดด
- ขนาดตายตัว: เส้น 2px, จุดเส้นผ่านศูนย์กลาง ≥ 8px พร้อมวงแหวนสีพื้น 2px,
  แท่งหนาไม่เกิน 24px ปลายมน 4px ฐานเหลี่ยม, เส้นกริดเป็นเส้นทึบบาง (ไม่ใช่เส้นประ)

### ตัวเลขบนหน้าจอ

`tabular-nums` (ผ่านคลาส `numeral`) ใช้เฉพาะที่ตัวเลขต้องเรียงตรงกันในแนวตั้ง —
ในตารางและบนแกนกราฟ **ห้ามใช้กับตัวเลขใหญ่เดี่ยวๆ** อย่างค่าบนการ์ด KPI เพราะ
การบังคับให้ทุกหลักกว้างเท่าเลข 0 ทำให้เลขอย่าง 121 ดูหลวมผิดปกติที่ขนาดใหญ่

## ตัวเลือกช่วงเวลา

`PeriodPicker` เป็นตัวควบคุมที่คนใช้บ่อยที่สุดในระบบ จึงมีกฎของตัวเอง

- **ตัวเลือกสำเร็จรูปมาก่อน เป็นรายการแนวตั้ง** (ทั้งปีงบ, เดือนล่าสุด, 3/6 เดือน
  ล่าสุด, ครึ่งปี, ไตรมาส) แล้วค่อยมี "เลือกช่วงเอง" ซ่อนใต้เส้นคั่น — ไม่มีใคร
  อยากสู้กับตารางปฏิทินเพื่อเลือกคำว่า "ไตรมาสที่แล้ว"
- **ปุ่มบนหน้าจอเขียนช่วงจริงออกมาเป็นภาษาคนเสมอ** ("ต.ค. 2567 – ก.ย. 2568")
  ไม่ใช่ "เลือกไว้ 5 เดือน" ซึ่งบังคับให้เปิดเข้าไปดูทุกครั้งว่ากำลังดูช่วงไหน
- **เลือกเป็นช่วง ไม่ใช่ติ๊กทีละเดือน** คลิกเดือนเริ่มแล้วคลิกเดือนสุดท้าย
  (โหมด `multi` ที่เลือกเดือนไม่ต่อเนื่องได้มีไว้ให้หน้าเปรียบเทียบเท่านั้น
  ซึ่งการหยิบ มิ.ย. มาเทียบกับ ก.ย. คือจุดประสงค์ของหน้า)
- **ตัวเลือกที่ข้อมูลไม่ครบยังกดได้** แล้วเขียนกำกับว่าได้กี่เดือนจากกี่เดือน
  แทนการปิดปุ่มเงียบๆ ซึ่งผู้ใช้เดาไม่ถูกว่าทำไมกดไม่ได้

## ชั้นดึงข้อมูล

หน้าจอไม่ยิง API เองสำหรับข้อมูลที่ใช้ซ้ำ — เรียกผ่าน composable ใน
`src/api/queries.js` ซึ่งสร้างบน TanStack Query (ดู [ADR-0009](../decisions/0009-tanstack-query-as-the-data-layer.md))

```js
import { useReferenceData, useMonthlyKpi } from "../api/queries";

const { buildings, divisions, departments } = useReferenceData();
```

ที่ได้มาฟรี: cache ข้ามหน้า, ยุบคำขอที่ซ้ำกันให้เหลือครั้งเดียว, คงข้อมูลเดิมไว้
ระหว่างโหลดชุดใหม่ และรีเฟรชเบื้องหลังเมื่อข้อมูลเก่าเกินกำหนด

**ถ้าเพิ่มหน้าที่แก้ข้อมูลอ้างอิง** ต้องสั่ง `invalidateQueries` ของ key นั้น
หลังบันทึก ไม่งั้นหน้าอื่นจะเห็นข้อมูลเก่าได้นานถึง 30 นาที

## ความหนาแน่นและโหมดสี

ผู้ใช้เลือกเองได้จากเมนูบัญชีบนแถบบน ทั้งสองอย่างถูกจำข้ามเซสชันและถูกตั้งค่าตั้งแต่ก่อน CSS วาดหน้าจอครั้งแรก (สคริปต์เล็กๆ ใน `index.html`) เพื่อไม่ให้เห็นหน้าจอกระพริบเป็นโหมดอื่นแวบหนึ่ง

| attribute ที่ `<html>` | ค่า |
|---|---|
| `data-mode-pref` | `light` / `dark` / `system` (สิ่งที่ผู้ใช้เลือก) |
| `data-mode` | `light` / `dark` (โหมดที่ใช้จริง) |
| `data-density` | `compact` / `default` / `relaxed` |

ความหนาแน่นเปลี่ยนค่า `--row-py`, `--row-px`, `--field-h` และ `--stack` ซึ่งตารางและฟอร์มอ่านไปใช้ — ไม่ต้องมีเงื่อนไขในแต่ละหน้า

โหมดมืด **ไม่ใช่การกลับสีของโหมดสว่าง** บนพื้นมืด แผ่นที่ลอยสูงกว่าต้องสว่างขึ้น ไม่ใช่มีเงามากขึ้น (เงาดำบนพื้นดำแทบไม่สื่ออะไร) semantic token จึงถูกกำหนดแยกกันทั้งสองโหมด และพื้นหลังใช้เทาอมฟ้าเข้มไม่ใช่ดำสนิท เพื่อลด halation ของตัวหนังสือขาวที่ทำให้ล้าตาเมื่ออ่านนานๆ

## ชุด component

ทั้งหมด import จาก `src/ui` ที่เดียว

```js
import { UiButton, UiCard, UiDataTable, UiField, UiInput } from "../ui";
```

ตัวที่ควรรู้จักก่อนเขียนหน้าใหม่

| component | ใช้เมื่อ |
|---|---|
| `UiPageHeader` | หัวเรื่องของทุกหน้า — ให้ระยะขอบและขนาดตรงกันทั้งระบบ |
| `UiCard` | กล่องเนื้อหาทุกกล่อง มี slot `header` / `actions` / `footer` |
| `UiButton` | ปุ่มทุกปุ่ม หนึ่งหน้าจอควรมี `variant="primary"` ได้ปุ่มเดียว |
| `UiField` + `UiInput`/`UiSelect`/`UiCombobox` | ช่องกรอกทุกช่อง — `UiField` ผูก label, คำอธิบาย และข้อความ error เข้ากับ input ให้อัตโนมัติ |
| `UiDataTable` | ตารางทุกตาราง — ค้นหา เรียง แบ่งหน้า ซ่อนคอลัมน์ ส่งออก Excel และแปลงเป็นการ์ดบนมือถือ มาให้ในตัว |
| `UiModal` | หน้าต่างซ้อน — ขังโฟกัส คืนโฟกัส ปิดด้วย Esc มาให้แล้ว |
| `UiEmpty` | สถานะว่าง — บังคับให้ตอบว่า "ทำอะไรต่อ" ไม่ใช่แค่บอกว่าไม่มีข้อมูล |
| `UiStat` | การ์ดตัวเลขสรุป |

`UiCombobox` ใช้แทน `UiSelect` เมื่อรายการยาวเกินกว่าจะกวาดตาหา (แผนกเป็นร้อย เครื่องเป็นพัน) รองรับทั้งเลือกเดี่ยวและเลือกหลายรายการ

## ข้อความบนหน้าจอ

- **ปุ่มเขียนเป็นคำกริยาที่จะเกิดขึ้นจริง** — "ลบเครื่องนี้" ไม่ใช่ "ตกลง" เพราะคนอ่านแค่ปุ่มแล้วกด โดยไม่ได้อ่านคำถามด้านบน
- **ข้อความ error บอกสิ่งที่ต้องทำ** — "กรอกชื่อยี่ห้อก่อน" ไม่ใช่ "ข้อมูลไม่ถูกต้อง"
- **สถานะว่างต้องมีทางออก** — บอกว่าทำไมถึงว่าง และปุ่มที่พาไปทำสิ่งที่ควรทำต่อ
- **ตัวเลขค่าใช้จ่ายต้องกำกับเสมอว่าหัก 20% แล้วหรือยัง** เพราะเป็นเลขที่ถูกเอาไปเทียบกับใบแจ้งหนี้จริง

## สิ่งที่ห้ามทำ

1. **ห้ามเขียนคลาสสีของ Tailwind ตรงๆ** (`bg-gray-50`, `text-blue-600`) — ไม่สลับตามโหมดมืดและไม่ผ่านการตรวจ contrast
2. **ห้ามเขียนปุ่ม ช่องกรอก ตาราง หรือหน้าต่างซ้อนขึ้นใหม่ในหน้า** — ของใน `src/ui/` รับผิดชอบเรื่องคีย์บอร์ดและโปรแกรมอ่านหน้าจอไว้ให้แล้ว
3. **ห้ามใช้สีเป็นวิธีเดียวในการสื่อความหมาย** (WCAG 1.4.1) — ป้ายสถานะทุกใบต้องมีข้อความ ไม่ใช่จุดสีเปล่าๆ
4. **ห้ามใส่ข้อมูลที่จำเป็นต่อการตัดสินใจไว้ใน tooltip** — บนหน้าจอสัมผัสไม่มี hover ข้อมูลนั้นจะหายไปเลย
5. **ห้ามแก้ค่าสีของกราฟด้วยสายตา** — ต้องรันตัวตรวจ colorblind ใหม่ทั้งสองโหมดทุกครั้ง
6. **ห้ามวางตัวกรองไว้ในการ์ดกราฟใบใดใบหนึ่ง** — ตัวกรองอยู่แถวเดียวเหนือทุกอย่างที่มันคุม
7. **ห้ามเอา `AuroraCanvas` ไปวางหลังตาราง กราฟ หรือฟอร์ม** — ใช้ได้แค่หน้าล็อกอินกับแผงสรุปบนสุดของแดชบอร์ด (ดูหัวข้อถัดไป)

## artwork และ "ลายเซ็นภาพ"

ระบบมี artwork ชิ้นเดียวคือ `components/AuroraCanvas.vue` — ชั้นแสง teal→ส้มจากสี
ในโลโก้โรงพยาบาล เป็น CSS ล้วน ไม่มีไลบรารีและไม่มี WebGL

**ใช้ได้สองที่เท่านั้น: หน้าล็อกอิน และแผงสรุปบนสุดของแดชบอร์ด**

เหตุผลไม่ใช่รสนิยม — พื้นหลังที่ไม่คงที่ทำให้ **วัด contrast ของตัวหนังสือไม่ได้**
และตัวเลขในระบบนี้ถูกเอาไปเทียบกับใบแจ้งหนี้จริง จุดที่วาง artwork ได้จึงต้องไม่มี
ตัวเลขที่ต้องอ่านเทียบกันอยู่บนนั้นเลย มีแค่หัวเรื่องกับคำอธิบาย

กฎที่มาคู่กัน

- **เล่น entrance ครั้งเดียวไม่เกิน 600ms แล้วหยุดถาวร** ระบบนี้คนเปิดทิ้งไว้ทั้งวัน
  ไม่ใช่หน้า landing ที่คนอยู่ 30 วินาที พื้นหลังที่ขยับตลอดเวลาในสายตาข้างๆ
  ทำให้ล้าและกวนสมาธิตอนกรอกตัวเลข
- **ตัวหนังสือบนแผงที่มีพื้นเข้มเสมอ ใช้ `--on-aurora*` ไม่ใช่ `--ink-invert`**
  เพราะ `--ink-invert` กลับขั้วตามโหมด แต่พื้นของแผงนั้นเข้มทั้งสองโหมด
- ด้วยเหตุผลเดียวกัน ชั้นแสงบนพื้นเข้มใช้ `--aurora-dark-*` ที่ไม่สลับตามโหมด
  ส่วน `--aurora-1..3` ที่สลับตามโหมดใช้กับแผงที่พื้นเปลี่ยนตามโหมดจริงๆ เท่านั้น
